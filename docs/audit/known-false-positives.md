### `sort()` 缺比较函数 · 5 处 · CRITICAL

|          |                                                                                                          |
| -------- | -------------------------------------------------------------------------------------------------------- |
| 位置     | `generate-reexports.mjs:35`、`check-design-system-exports.mjs:63/81/121`、`check-design-system.mjs:2798` |
| 工具主张 | 提供比较函数，最好是基于 `String.localeCompare`                                                          |
| 结论     | **误报**，不改                                                                                           |

**原理。** `Array.prototype.sort()` 不带比较函数是把元素转成字符串、按 **UTF-16 码元**
比较——跨机器、跨 locale 完全确定。而 `localeCompare` **按 locale 变**（瑞典语里
`å` 排在 `z` 之后）。

**照它改会发生什么。** 这几处排的是生成物里的导出名与键名，生成物入仓、由
`--check` 逐字节对账。换成 `localeCompare` 之后，同一份源码在不同 locale 的机器上
会生成**不同顺序**的文件，`--check` 于是在别人的机器上假红。

**也就是说工具警告的那个后果，恰恰由照它改造成。**

> 第一轮审计报告初版写的是「排序不稳会让对账在别人机器上假红，sort 那几处值得
> 先看」——因果写反了。报告已勘误。

**复核期限**：2027-02，或本仓开始用 `sort()` 排**给人看的**列表时（那时 locale
敏感排序才是对的）。

### ~~非交互元素挂点击处理~~ · `MetricListCard.tsx:151` · MINOR

> **这条判错了，2026-08-26 撤销。** 保留原文与更正，因为「误报登记里出现过一条
> 真报」本身就是这份文件最该被记住的事。

**原判**：误报，不改。理由是「键盘 Enter 在内层按钮上会**产生一个冒泡的 click**，
同样被那个 `stopPropagation` 拦住，所以键盘路径也是通的」。

**错在哪**：漏了一步。**keydown 先于 click 发生**，而卡片的 `onKeyDown` 对任何
冒泡上来的 Enter/Space 都响应——它 `preventDefault()` 掐掉按钮的原生激活，再把
整卡的 `onClick` 触发一遍。于是：

> **键盘用户按不到行操作，反而进了详情。** 鼠标那条路有 `stopPropagation` 护着，
> 完全看不出问题。

写指标卡回归测试时实测出来：按 Enter，行操作的 `onClick` 调用次数是 **0**。

**已修**：卡的 `onKeyDown` 加一句 `if (event.target !== event.currentTarget) return`
——焦点在卡内的控件上时，那个控件 own 这次按键。同时补了正向用例（卡本身聚焦时
Enter 与 Space 仍要响应），免得把「该触发」也一起修没了。

**教训**：工具报的位置是对的，只是它给的理由（「缺键盘监听」）和真实病因
（「键盘监听管得太宽」）不是一回事。**看懂工具指的地方，不等于看懂那里的问题。**

### `pnpm install` 缺 `--ignore-scripts` · `setup-node-pnpm/action.yml` · 已修

|          |                                                    |
| -------- | -------------------------------------------------- |
| 工具主张 | 给 `pnpm install` 加 `--ignore-scripts`            |
| 结论     | **报得对，已加**。同时补了一道 pnpm 层的显式白名单 |

**担心为什么是对的。** 这个 action 被 `publish-design-system.yml` 用，那个 job 有
`packages: write` 权限。依赖的 `postinstall` 在那里执行，等于把发布凭据交给依赖树。

**处置：两道都上。**

| 载体                                                 | 管到哪                     | 作用                                                 |
| ---------------------------------------------------- | -------------------------- | ---------------------------------------------------- |
| `pnpm-workspace.yaml` 的 `onlyBuiltDependencies: []` | **所有安装**，含开发者本机 | 把「谁可以跑脚本」变成一份**可清点、进 diff** 的名单 |
| action 里的 `--ignore-scripts`                       | 只有 CI                    | 纵深的第二道，不依赖 pnpm 的默认行为                 |

**名单确实生效，不是摆设。** 实证：把 `esbuild` 临时加进去再装一次，它的
postinstall 当场跑了（`esbuild postinstall$ node install.js`），拿掉就不跑。

⚠ pnpm 仍会打印 `Ignored build scripts: …`——**那不是字段没被读取**，只是它在
报告跳过了谁。别因为这行以为配置没生效。

---

**这一条本身踩过一次坑，值得留着。**

初次处置判定**不加** `--ignore-scripts`，给的两条理由是：

1. 它拦不住任何东西——pnpm 10 起依赖的构建脚本默认不执行（实测打印
   `Ignored build scripts: esbuild, sharp, unrs-resolver`）。**这条成立。**
2. 它会连本仓自己的 `prepare`（husky）一起关掉。**这条把成本说重了。**

第 2 条错在**没分清这个 action 用在哪**。它只在 CI 用（`ci.yml` 两处、
`publish-design-system.yml` 一处），本机开发不走它；而全仓唯一的生命周期钩子就是
`prepare: husky || true`，装的是 git 钩子——**CI 不用 git 钩子**。所以在 CI 里这个
开关的代价是零。

清空 `node_modules` 带这个开关重装后实测：type-check / build / guardrails /
192 条用例全过。于是改成两道都上。

> **判据：说一个开关「代价太大」之前，先查清它作用在哪个范围。** 第 1 条是关于
> 行为的、查过就成立；第 2 条是关于代价的，而代价永远是「对谁的代价」——
> 范围没查清，成本估计就是凭印象。

**复核期限：** pnpm 主版本升级时。若 pnpm 11 改了默认行为，第 1 条即失效，而两道
防线正是为这一天准备的。

### ~~`Toast` 用 `Math.random` 生成通知 id~~ · 已修

|          |                                                               |
| -------- | ------------------------------------------------------------- |
| 工具主张 | `Math.random` 不是密码学安全的                                |
| 结论     | **理由不适用，但结论可取**。2026-08-26 (6.0.5) 换成单调计数器 |

**理由为什么不适用。** 这个 id 是 React 的 key 与 dismiss 时的查找键，
**不需要不可预测**——被猜中也什么都做不了。

**但也没有换成 `crypto.randomUUID`。** 那是**安全上下文限定**的 API：在 http 页面
上（内网工具、局域网预览）`crypto.randomUUID` 是 `undefined`，调用直接抛。
为了消一条不适用的告警而引入一个只在一半环境里存在的 API，是把告警换成故障。

**换成了单调计数器**，因为对这个用途它比两者都合适：随机数**可能碰撞**（同一毫秒
连发两条，36 进制尾巴还撞上），表现是两条通知共用一个 React key、后一条把前一条
顶掉，且只在手快时偶发；计数器按构造不会。而且它**可测**——「两条 id 必须不同」
对随机数只是大概率成立，对计数器是恒真。已由三条变异验证。
