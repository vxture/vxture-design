# 000 · 文档体系

版本：2.0.0 ｜ 日期：2026-08-27

这份文档只回答一个问题：**一个具体的疑问，该去哪儿找答案。**

它存在的理由：没有分工说明时，同一个问题会在两处各有半个答案，而两处都不知道对方
存在。

## 1. 两层，读者不同

判据是**读者**，不是主题：

| 层       | 读者                                     | 载体               | 回答                                   |
| -------- | ---------------------------------------- | ------------------ | -------------------------------------- |
| 仓内     | **实现者**——要改 DS 的人                 | 本仓 `.md`         | 怎么改、改的时候守什么规矩、怎么发出去 |
| Artifact | **跨仓读者**——消费方、评审、半年后的自己 | claude.ai artifact | 这套系统是什么、能力在哪、现在什么状态 |

两层**不互相复制**。同一件事只在一处写全，另一处引过去。

判断一份新文档该进哪层，问一句：**读者需要能改代码吗？**需要就进仓内，不需要就
进 Artifact。「消费方要知道有哪些件」——不需要改 DS，进 Artifact；「加一个件要
更新哪些登记处」——要改，进仓内。

### 2.4 机器可执行的那一份

`pnpm guardrails` 串起的 **10 条守卫也是文档**，而且是唯一会在写错时出声的一份。
每条守卫的头注释写明「补的是哪个盲区」与「实测抓到过什么」——那段注释是它存在的
理由，删了它这条守卫就没人知道为什么不能删。

10 条**全部有变异用例**（`pnpm test:guardrails`）。没有这一层，一条坏掉的守卫和一条
正常工作的守卫看起来完全一样：都是绿的。

`packages/*/tests/` 下的用例是第三份：**契约里可执行的那部分**。写用例时读出来的契约
写在用例的注释里，那些注释解释的是「为什么这样才对」，规范文档解释的是「是什么」。

规范与守卫的分工：**规范写判据，守卫写判据里可机器判定的那部分**。两者不是同一
件事的两个副本——一条规范往往只有一半能机器判定（见审计报告「机器守得住什么」）。

## 3. Artifact：给跨仓读者

对齐 Karda / Atlas / Runos 的文档集形制，同一套版式与配色。

| 文档       | 回答                                           | 状态     |
| ---------- | ---------------------------------------------- | -------- |
| 审计报告   | 出过什么问题、怎么逃过检查的、还开着什么       | ✅ 已建  |
| 系统架构   | 三包怎么分工、依赖朝哪、边界在哪、怎么构建发布 | ✅ 已建  |
| 能力登记册 | 有哪些件、各在哪一层、什么状态                 | ✅ 已建  |
| 发版说明   | 升到这一版要改什么、不用改什么、怎么确认迁完   | ✅ 已建  |
| 接口文档   | 公开面是什么：入口、导出、CSS 子路径           | ✅ 已建  |
| 设计语言   | token 两层、语气六档、危险两档、各条刻度       | ✅ 已建  |
| 消费方现状 | 五个门户装了哪版、迁到哪一步                   | **不建** |

**发版说明与 CHANGELOG 的分工**：CHANGELOG 写给**本仓**——为什么这么改、
病因是什么、判据在哪。发版说明写给**消费方**——你要改什么、不用改什么、
你以前做的绕法现在能不能撤。同一次发布，两种读者，不互相替代：把病因塞进发版说明
会淹没「你该做什么」，把迁移步骤塞进 CHANGELOG 则半年后没人找得到。

**「消费方现状」为什么不建**：那份数据不在本仓，DS 看不到 portals 的 lockfile，
写出来的第一天就是过期的。消费方的版本与迁移状态由消费仓自己登记；DS 这边只保证
「怎么迁」写清楚（各版 CHANGELOG 的迁移段）。

宁可缺一份文档，也不要一份**看起来权威、实际过期**的文档——审计报告里那条
「一份自称完整的清单比没有清单更坏」是同一个判据。

## 3.1 形制：抄，不要理解

Artifact 层的版式、配色、组件类名全部来自 **Karda 文档集**。参照物入仓：
`docs/artifacts/_reference-karda-audit.html`（已裁掉宿主注入的 frame-runtime）。

三份 DS 文档的 HTML 底本也入仓（`docs/artifacts/*.html`），**不是只存在于发布出去
的那个 URL 里**——没有底本，下一次修改就只能靠记忆重建。

### 判据

**同形的部分逐项相等，扩展排在原有之后。**

|            | 参照物        | DS 文档                                                                |
| ---------- | ------------- | ---------------------------------------------------------------------- |
| 导轨组顺序 | 文档集 → 本页 | 文档集 → 本页 → **同族**（扩展）                                       |
| 配色       | 家族共用      | 同左，**刻意不改**——每换产品就换配色的文档系统是三个产品，不是一个系统 |
| 识别       | `rail-brand`  | 同左，靠品牌位区分而非颜色                                             |

扩展是允许的（「同族」这一组 Karda 没有），**重排原有的不是扩展，是替换**。

### 为什么要有守卫

第一版三份文档的 CSS 是逐字节 `sed` 抽出来的，一字不差；导轨是**照着理解重打的**，
于是组顺序整个反了，组名也擅自改成了「DS 文档集」。

病因不是手滑，是**把结构变成描述、再从描述重建**——顺序活不过摘要。而发布前的
校验查的是标签配平、锚点不悬空、主题三态，全是**页面自洽性**，一次都没有拿参照物
本身对账。

`scripts/docs/check-doc-shape.mjs` 就是那次对账，已进 `pnpm guardrails`。

## 4. 加一份文档之前

1. **先找它该并进哪一份。** 大多数「新文档」其实是某份已有文档缺的一节。
2. **确认读者。** 读者要改代码就进仓内，否则进 Artifact。
3. **能机器判定的部分，同时落成守卫。** 只写进散文的判据，只对读过那一页的人
   生效——本仓四个 major 全部起因于此。
