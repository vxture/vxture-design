# 070 · 审计方法

适用版本：**DS 14.0.0** ｜ 更新：2026-09-24 ｜ 范围：本仓的审计与回归测试方法

**这一份写的是怎么审、以及方法在哪里会失灵。** 每一轮审出了什么写在 Artifact 的
「审计报告」里，不在这里。

下面每条规则都是踩出来的，但只留规则与判据——具体是哪一轮踩的、当时绕了多少弯，
留在各次 PR 与 CHANGELOG 里。

## 1. 十条不要相信

### 1.1 不要把「绿」当成「查过」

> **守卫坏掉的表现，和它正常工作的表现，都是「绿」。**

`check-design-system` 曾有四条检查是死的——6 处字面量退格符让它们的正则永远匹配
不上，而整条链照常打印「passed」。发现它靠的是另一个工具因另一条无关理由报了
「控制字符」。

**对策**：`pnpm test:guardrails`（对每条守卫做变异测试）。审计**第一步**就跑它，
在读任何守卫输出之前——后面所有结论都建立在守卫说真话的前提上。

同类：**一条写下来没人验的理由，和一条从没生效过的守卫，坏的方式完全一样。**
`self-test.mjs` 里曾有一张「未做变异测试的守卫」表，三条各附一条理由；查下来两条
不准、一条完全错。那张表长得像已经想过了——那正是它的危险处。现在**每条守卫都有
变异用例**，覆盖数由 `self-test.mjs` 从 `package.json` 的链条算出来，不写死。

「没有跳过项」这句以前也只是写在这里的一句话。现在它是机器判的：
`pnpm test:guardrails:strict` 下任何跳过都判失败（见 §1.7）。

### 1.2 不要转述工具的结论

工具给的是**信号**，不是结论。每条要写进报告的发现，都必须**自己看过那段代码**并
能说清：它错在哪、照它改会发生什么。说不清就不写。

已判过的误报记在 `docs/audit/known-false-positives.md`，带原理与复核期限。

### 1.3 不要把结构变成描述再从描述重建

> **顺序活不过摘要。**

三份 Artifact 文档的 CSS 是逐字节抽出来的，一字不差；导轨是照着理解重打的，组顺序
整个反了。而发布前的校验查的全是**页面自洽性**（标签配平、锚点不悬空、主题三态），
一次都没有拿参照物本身对账。

**对策**：能复制就不要复述；要比对就写脚本比对（`check-doc-shape`），不要靠眼睛。

### 1.4 消费端报来的「根因在 DS」，先做对照组

> **先造一个不含 DS 的对照组。** 症状在对照组里照样出现，讨论就结束了；照样不出现，
> 才轮到看 DS 的实现。

典型形状：React 的 key 警告点了两个名字（收下数组的那个 DS 件、元素被创建的那个
页面），**真正拼出无 key 数组的中间层一个字都没被提到**。顺着警告里的名字走，一个
通向 DS、一个通向页面，恰好绕开真凶。裸 `<div>` 的对照组报同一条，DS 就此出局。

配套判据：**这类警告不能压。** `[a, b].filter(Boolean)` 少一个成员时后面的会落到前
面的索引上，React 按索引复用实例，同类型兄弟之间状态会串。DS 用 `Children.toArray`
之类的手法把警告吃掉，等于把消费端的真缺陷盖住。DS 该做的是保证自己不出这个形状
——已落成 `packages/design-ui/tests/setup.ts` 里的 key 守卫，全套用例零警告。

### 1.5 不要接受一个太顺理成章的解释

平台故障进行时，「还没轮到我」是个太容易接受的解释——它解释得了现象，但没有被验证过。

判据一般只要一个字段。GitHub Actions 的孤儿 run 与真排队的 run 都显示 `queued`，
区分它们的是 `updated_at`：真在排队的会被反复更新，孤儿的 `updated_at` 永远等于
`created_at`。更直接的信号是**接口之间自相矛盾**（取消接口说已完成、查询接口说在
排队）——两边对不上就是状态坏了，那一刻就该动手。

孤儿 run 的解法：`gh pr close` + `gh pr reopen` 重新触发 `pull_request` 事件。

> 这与 §1.1 是同一条：**「说得通」不等于「查过了」。**

### 1.6 也不要把红当成「查出问题了」

`pnpm format:check` 在 Windows 上曾经**恒红**：112 个文本文件是 CRLF，其中 89 个落在
format 的 glob 内，全部报「不合格式」——而它们的内容一个字都没错。

> **一个恒红的检查什么都没查**，而且比一个恒绿的更费时间：它每次都要求你重新说服
> 自己「这次也是行尾问题」，而真出现一次格式问题时没人分得出来。

§1.1 说的是不要把绿当成查过；这一条是它的反面。**两者的处置也相反**：恒绿要补变异
测试去戳穿它，恒红要**去掉那个恒定项**，让它重新变成信号。

这一条已修（`.gitattributes` 归一为 LF，见 §1.6.1）。留在这里是因为判据本身还在：
下一个恒红的检查出现时，别再花一轮去习惯它。

### 1.6.1 修它的过程本身踩了 §1.2 与 §1.5

根因很简单：**没有 `.gitattributes`**，检出行尾就由各人机器上的 `core.autocrlf` 决定
（Windows 默认 true → CRLF），而本仓没有 prettier 配置文件，`endOfLine` 用的是它的默认
值 `lf`。CI 跑在 Linux 上、检出就是 LF，所以从没在 CI 上现形。

但**中间量错了一次，差点把结论推翻**。用 `grep -c $'
'` 数 CR，shell 把 `$'
'` 吃掉，
数出来是 0；据此得出「文件里没有 CR，行尾说不成立」，而实际有 274 个。

两条判据同时适用：

- **§1.2**：那个 0 是工具给的信号，不是结论。换 node 直接读字节，答案立刻反过来。
- **§1.5**：「行尾问题」是个太顺理成章的解释——但当中间量说它不成立时，先怀疑量法，
  再怀疑结论。**推翻一个正确结论的，往往是一个坏掉的测量，而不是新证据。**

> 在这台机器上，凡是要数控制字符 / 反斜杠的，一律别走 shell 的引号。用 node 或 python
> 读字节。本轮同一个坑踩了六次。

### 1.7 不要把「跳过」当成「通过」

> **守卫的 miss 路径写成「跳过」，它就能在什么都没验的情况下报绿。**

2026-09-24 的一轮梳理里，同一个形状抓到两处，彼此独立：

| 处                          | 触发               | 表现                                                                                       |
| --------------------------- | ------------------ | ------------------------------------------------------------------------------------------ |
| `check-server-entry-safety` | 从非仓库根目录调用 | **一个入口都没验**却 `error: 0   skipped: 2` 然后 EXIT=0                                   |
| `self-test.mjs` 自己        | 缺构建产物         | 打印「覆盖：全部 12 条守卫都有各自的变异用例」紧接着「自测通过（**10** 条守卫…）」，EXIT=0 |

**触发条件不同，形状相同**——这才是它值得单独成条的原因：下一次它会由第三种原因
触发，认形状比认原因有用。

两处的共同形状是**两件事叠在一起**：

1. 找不到目标时走的是 `skipped += 1` 而不是报错；
2. 收尾 `process.exit(failed > 0 ? 1 : 0)` 只看 `failed`，不看 `skipped`。

第二处最毒：上下两行凑在一起**声称 12 条全覆盖、实测只有 10 条、然后报通过**。
极端情形是全部用例被跳过，它会打印「自测通过（0 条守卫…）」并 EXIT=0——一个测不到
任何东西的自测报绿，正是 §1.1 反对的那件事。

**对照组说明了问题不在「路径会跑偏」**：当时全仓有 18 个脚本用 `process.cwd()`
定位仓库根，同样会跑偏。实测了其中 11 个（10 个检查器 + 1 个生成器）从错误目录跑，
**除 `check-server-entry-safety` 外全部大声 EXIT=1** —— 崩掉是安全的失败模式，
一眼就知道调用方式不对。

所以危险不来自跑偏，来自**跑偏之后不出声**。差别只在 miss 路径是「跳过」还是报错。

**判据三条**：

- **miss 路径要么报错，要么可切换成报错。** 本地还没 build 时不拦人是合理的，
  但那必须是一个**档**，不是唯一行为。两条守卫现在都有 `--require-artifacts`，
  CI 跑严格档（`lint:server-entry:strict` / `test:guardrails:strict`），默认档留给本地。
- **仓库根由 `import.meta.url` 派生，不跟 `process.cwd()` 跑。** 守卫认的是仓库里的
  固定位置，不该受调用目录影响；让 miss 路径**够不着**比让它出声更根本。
- **验证守卫改动时比对输出，不比对退出码。** 「报绿」和「干了活」是两件事：
  改完后要确认从子目录跑的输出与仓库根**逐字一致**，而不是都 EXIT=0 就算过。
  `self-test.mjs` 里读 `package.json` 算覆盖数那处漏改，就是因为它排在 12 条变异
  全打 ✓ 之后才崩——只看前半截输出会以为已经好了。

### 1.8 设计稿上画的，不等于组件规格

> **一个实例把组件改成什么样，是这一处的事；组件本体是什么样，才是规格。**

2026-09-24 按 Figma 对齐五个节点时，第一条结论差点写反。

两个验证码弹窗里的 OTP 格子是 **56px、每格独立描边、`radius-xl`**，与当时 DS 的
32px 连体格子完全不同。照着改，就是一次波及全部消费方的改版。

查组件本体后结论反过来：

|      | Figma `InputOTPSlot` **组件本体**             | 当时的 DS                              |
| ---- | --------------------------------------------- | -------------------------------------- |
| 尺寸 | `var(--space-control-md)` = 32                | `h-control-md` = 32                    |
| 圆角 | `radius-md`                                   | `first:rounded-l-md last:rounded-r-md` |
| 形态 | `position` = first/middle/last/single（连体） | 同                                     |

**逐项一致，一个字都不用改。** 56px 只存在于那两个弹窗的**实例覆盖**上。

**判据是看变量绑定，不是看渲染结果**。那两个实例绑的是
`--foreground` / `--radius-xl` / `--border-width-thin` / `--control-border`
——**没有任何尺寸变量**，56 是个裸数字；圆角也从组件绑的 `radius-md` 被改成了
`radius-xl`。一处连自己的尺寸都没走 token 的覆盖，不构成"设计改了规格"的证据。

**怎么分辨**：

- **查组件本体**：`get_metadata` 打开组件节点，看它的变体矩阵（`state` /
  `position` / `size`）与 `get_variable_defs` 的绑定。变体矩阵就是这件东西
  **被设计成有几种形态**，比任何一处渲染都权威。
- **看元素类型**：`instance` 是组件实例，`frame` 是手搭的稿子。同一份稿子里
  两者常常混着——本轮节点 5 的 `TenantInfo_Title` / `workspace-item` 都是
  `frame`，只有 Separator / 图标 / 药丸是 `instance`。frame 里的像素值是效果图，
  不是规格。
- **看组件说明**：标了 `Source-aligned packages/design-ui/...` 的组件是与代码
  对齐过的，它和 DS 的差异才值得当成真差异。
- **搜一遍库**：`search_design_system` 确认没有第二个同类组件（比如一个"大号
  OTP"），否则可能只是你没找到那个才是规格的件。

**处置**：

本体与 DS 一致、只有实例不同 → **加一档**，不改默认（`InputOTP` 因此有了
`size="lg"`，默认档一个字没动）。要改默认，得先有组件本体层面的依据。

裸数字落到 DS 时映射到最近的 token 档，不照抄——本轮 56px 走的是既有的
`--space-control-3xl`（= 56px，跟随密度三档），不是写死 `56px`。

> 与 §1.2 是同一条：**渲染结果是信号，不是结论。** 差别只在这次信号来自
> Figma 而不是 SonarCloud。

### 1.9 不要把「没查到」当成「没有」

> **查到了什么，结论自带证据；没查到什么，结论的证据是「我挑的那组词」。**

两种结论的可信度天差地别，而它们在报告里长得一模一样。

肯定结论指得出实物——那个文件、那一行。否定结论指不出任何东西，它的全部依据
是**检索面覆盖到了该覆盖的地方**，而检索面是查的人自己划的，从未被检验。

2026-09-24 按 Figma 对齐时踩到：初查"DS 里有没有用户面板"，检索词是
`UserPanel|TenantPanel|Workspace|ScopeButton`。**`ShellUserMenu` 一个词都不含**，
于是结论写成"DS 没有用户面板成品"，并据此提议新建 `ShellUserPanel`。

而它就是用户面板——头部、槽位段、链接段、偏好段、动作段，与 Figma 那份逐段
对应、顺序一致。差一点就造出第二个轮子，且是在"不要重复造轮子"被明确交代过
的前提下。

**这条与 §1.1 同构**：守卫报绿和"没查到"一样，都是**一个没有内容的结果**，
而没有内容的结果最容易被当成结论——它不刺眼，不需要解释，读起来像已经查过了。

**办法：否定结论必须换一个正交的检索面再查一遍。**

按名字查不到，就换一种查法：

- **按出口查**——公开导出清单（`design-system-exports.snapshot.json`）、产物的
  `.d.ts`、预览面注册表。本仓这三处最可靠：**一个件只要存在且公开，一定在这里
  露面，不管它叫什么名字。** 上面那次只要扫一眼导出清单就不会漏。
  注意导出清单只收**运行时导出**，类型不进（`InputOTPSize` / `ToggleSize` 都
  不在里面）——找类型要走 `.d.ts` 或 barrel，别在清单里查不到就下否定结论。
- **按结构查**——这一类东西该有什么 props、该 import 谁、该落在哪个 barrel。
- **按反向查**——谁在用这个概念（调用点、测试、文档），而不是这个概念叫什么。

**写法也要改**：否定结论写成「**我用 X 查过，没查到**」，而不是「没有」。
前者可被反驳——读的人一眼看出你没查哪儿；后者只能被相信。

### 1.10 不要相信一个自称完整的清单

> **覆盖面会变，写死的数字不会跟着变——而它不变的样子，和它正确的样子一模一样。**

这条是 §1.1 的一个具体形态，单独列出来是因为它**反复出现**，而且有明确解法。
2026-09-24 一轮里抓到下面这些，彼此独立：

| 处                           | 写的是             | 实际是 | 怎么坏的                                           |
| ---------------------------- | ------------------ | ------ | -------------------------------------------------- |
| `self-test.mjs` 的覆盖行     | 「全部 10 条守卫」 | 11 条  | 接第 11 条时它一个字都没变                         |
| `ci.yml` 守卫步骤注释        | 「十一道守卫」     | 12 条  | 同一行注释写着「**别在这里手抄**」，然后自己手抄了 |
| 四份文档                     | 「10 条守卫」      | 12 条  | 链条涨了，文档没人回来改                           |
| `check-doc-version` 的汇总行 | 「12 份文档」      | 20 份  | 把随包规范八份纳入覆盖后，它照样报 12              |

最后那处最能说明问题：**扩大覆盖面的那次改动本身，就是让这个数字变错的那次
改动**——而它不会因此报错，只会继续打印一个已经不成立的数。

`ci.yml` 那处最讽刺：作者已经知道这个坑、把告诫写在了同一行，还是手抄了一个
数字进去。**知道规则不构成防护**，这正是"为什么要有守卫"的原因。

**解法，按优先级**：

- **从事实算出来。** `self-test.mjs` 现在两边都取事实：链条读 `package.json` 的
  `guardrails` 串，用例读本文件的 `CASES`；`check-doc-version` 数它实际查过的
  文件数。算出来的数字不会过期，因为它没有"自己的记忆"。
- **能不写就不写。** 文档里的「10 条守卫」本轮是**直接删掉数字**，不是改成 12
  ——改成 12 只是把过期时间推到接第 13 条那天。说"守卫成一条链"就够了，
  数量随 `package.json` 走。
- **非写不可时，让它旁边有一条判据能发现它过期。** 没有这条判据，写下来的数字
  与 §1.1 里那张"未做变异测试的守卫"表没有区别：长得像已经想过了。

**识别信号**：凡是句子里出现「全部 N 个」「N 份」「N 条」，先问一句
**这个 N 是算出来的还是敲进去的**。敲进去的，就当它已经过期了，去数一遍。

**边界也要写明**，否则这条会被当成「任何数字都不许写」：

- 上表里那四行**引用的是当时的实测输出**（「声称 10 条、实际 11 条」），
  它们是证据不是断言，照原样留着才对。
- 本节所在的 §1 标题「十条不要相信」同样是写死的数字。它与上表四处的差别在于
  **判据就在紧邻的下方**——数一遍小节就知道对不对，而且每次加条目都必然经过
  这一行。写死的数字有没有问题，取决于**它离能验证它的事实有多远**。
- 真正危险的是那种**离事实很远、且改动时不会经过**的数字：一个在几十行外的
  `console.log`、一份在另一个目录里的文档、一条 CI 注释。

## 2. 顺序

每一步都不可跳过，且**顺序有意义**：先证明仪器可信，再用仪器。

| #   | 做什么           | 命令                                            | 为什么在这个位置                            |
| --- | ---------------- | ----------------------------------------------- | ------------------------------------------- |
| 1   | 工作树必须干净   | `git status --porcelain`                        | 后面几步会改真实文件再还原                  |
| 2   | **守卫自测**     | `pnpm test:guardrails`                          | 先证明仪器活着。这一步红，后面全部无效      |
| 3   | 基线快照         | `node scripts/audit/snapshot.mjs`               | 与上一轮 diff。测法与数字一起入仓，所以可比 |
| 4   | 跑全部守卫       | `pnpm guardrails`                               | 此刻它的「绿」才有意义                      |
| 5   | 逐包验证         | `pnpm -r type-check && pnpm lint && pnpm build` | 按依赖方向                                  |
| 6   | **组件行为测试** | `pnpm test`                                     | 自测证明仪器活着，这一条测件本身对不对      |
| 7   | 外部工具         | SonarCloud API                                  | 拿信号，不拿结论                            |
| 8   | 对照误报登记     | `docs/audit/known-false-positives.md`           | 别重新讨论已经判过的                        |
| 9   | 逐条核实         | ——                                              | 每条发现自己看代码，写清失败场景            |
| 10  | 写报告           | `docs/artifacts/audit.html`                     | 底本入仓，形制由 `check-doc-shape` 守       |
| 11  | 写入基线         | `node scripts/audit/snapshot.mjs --write`       | 给下一轮留下可比的起点                      |

## 3. 分类判据

按**缺陷是怎么逃过检查的**分，不按它在哪个文件——因为那才决定下一条同类缺陷会不会
再逃一次。四类够用：

| 类                   | 特征                   | 典型                                 |
| -------------------- | ---------------------- | ------------------------------------ |
| 静默失败             | 构建全绿，只是结果不对 | 类名哑火、挡位用错、body 锁死        |
| 契约只写在散文里     | 判据成文但没有载体     | `danger` 只染色不设防、文案出口      |
| **守卫自己停止守卫** | 表现是「绿」           | 退格符死正则、扫描面被白名单缩小     |
| 分层与打包的隐性约束 | 约束只写在运行时行为里 | server 入口崩、引用环、`Omit` 不分配 |

新发现如果四类都装不下，先怀疑是分类不够，再考虑加一类——**类别的价值在于它能预测
下一条**，不在于把清单填满。

## 4. 写行为测试的判据

到目前为止查出的真缺陷**全部**来自变异测试或「为了写用例而读契约」，**没有一条是
覆盖率数字追出来的**。所以这一节是本文最该照做的一节。

### 4.1 每条回归测试都要把缺陷放回去跑一次

> **不红，这条测试就是装饰。**

有些故障 jsdom 重现不了（依赖真实的竞争时序）。这时**换一个能稳定分辨两版的断言，
钉机制而不是钉症状**，并在注释里写明这个区别。

### 4.2 变异不红，先查代码，别急着加断言

> **变异留绿有两种解释：测试没钉住，或者代码里有条多余的路在兜着。**
> 先分清是哪一种。直接补断言，等于把那条多余的路一起焊死。

一条「退出时还原滚动」的变异不红，追下去发现根因是那个标着「组件卸载时清理」的
effect 依赖数组里带了状态——清理**每次依赖变化都会跑**，把正经的那次调用顶掉了。
补断言会把这个缺陷永久固化。

### 4.3 「不给就不渲染那一层」要数元素，不要数文字

把 `{action ? … : null}` 改成恒渲染，出来的是一个**空壳**——既没有文字也没有角色，
从内容上分辨不出，而它带着 `gap` 会留出一段说不清来路的空白。

> **这类分支一律数元素**（`root.children` 的长度），不数文字。

同一形状：`aria-hidden` 的断言写成「页面里存在某个 `aria-hidden`」会**被内层 svg
自带的属性满足**。断言要落在**那一层本身**上。

### 4.4 断言 className 按 token 比，不要 `toContain`

`toContain` 是子串匹配，而 Tailwind 的变体天然让一条类成为另一条的子串
（`dark:has-[…]:border-destructive/50` 含 `has-[…]:border-destructive`）。

```ts
className.split(" ").filter(Boolean).includes(token);
```

### 4.5 数图标个数分不出画的是哪一张

去向图标与 chevron 都只是一张 svg。要区分就拿一个已知形态的同款元素比 `innerHTML`。

同理，「有没有 svg」不能用来判断语气：`StatusBadge` 两种语气**都**自带前导图标。

### 4.6 「点下去不抛」要接 window 的 error 事件

**React 事件处理器抛出去的错不在 `user.click` 的 promise 链上。**

```ts
// 装饰：处理器抛了也照样 resolve
await expect(user.click(el)).resolves.toBeUndefined();

// 真的在抓
const onError = vi.fn();
window.addEventListener("error", onError);
await user.click(el);
window.removeEventListener("error", onError);
expect(onError).not.toHaveBeenCalled();
```

### 4.7 变异器分四种结局，只有一种算抓到

| 结局             | 含义                                     |
| ---------------- | ---------------------------------------- |
| 有断言变红       | **抓到**                                 |
| 全绿             | 洞在用例                                 |
| 文件编译不过     | **不算数**，回去把变异改成能编译的       |
| 炸在未捕获异常上 | **同样算洞**——缺陷炸了，但没有断言接住它 |

按「非零退出码 = 抓到」来判是危险的：那会把一条从没跑过任何断言的变异记成已验证。
成对修改（开闭标签之类）用一条变异带多处改动来表达，别拆成两条。

### 4.8 组件调组件的地方，问一句「这件事被做过两遍，还是一遍都没做」

> 单看本文件永远答不上来。答案在上游 `Root` 的 props 表里，和邻件的文件头里。

两个真缺陷是同一个形状：`Progress` 把 `value` 解构走后**没传回 Radix Root**（读屏器
永远听到「正在忙」）；`ShellUserMenu` 在 `StatusBadge` 自带的语气图标之外**又画了一个
对勾**。两条都不报错、不影响布局，读代码时那一行看起来都是对的。

`Progress` 那条另有一层：它是**照抄上游 shadcn 抄进来的 bug**。「结构照官方 X」此前
读起来是出处说明，现在它同时是一条线索——**上游的缺陷会一并抄进来，而「照抄上游」
通常被当作不必再审的理由。**

### 4.9 测试不许逼守卫开口子

用例放在 `packages/*/tests/` 而不是 `src/**/__tests__/`，因为 `src/` 下有两条守卫在扫
（`check-i18n-seam` 禁中日韩字符，而用例名是写给维护者的中文散文；
`check-preview-coverage` 要求 `components/` 下每个 `.tsx` 都有预览条目）。

**为了迁就测试而给守卫开豁免，是把安全网剪个洞。** 挪个目录就没有这个问题。

### 4.10 用例目录必须进 type-check

`tests` 不在 `tsconfig` 的 `include` 里时，用例可以断言一个**类型上根本不成立的用法**
——那条断言测的是一个不存在的世界。接上之后两个包一次报出 46 条真错误。

两个包的 `tests` 现已纳入 `pnpm -r type-check`。

## 5. 报告的硬要求

- **每条发现给出失败场景**：什么输入 → 什么错误结果。给不出就还没查清
- **写明是谁抓到的**：机器抓的写哪条守卫，人抓的写谁提的。最贵的几条发现来自消费侧
  评审，这件事必须写进报告，否则下一轮会高估机器
- **不写没验证的数字**。数字要带测法（见基线快照的 `how` 字段）
- **勘误留在原地**，不要把错的那段悄悄改掉——读者需要知道结论变过
