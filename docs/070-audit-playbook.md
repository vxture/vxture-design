# 070 · 审计方法

版本：1.0.0 ｜ 日期：2026-08-25 ｜ 依据：第一轮审计（design-ui 3.2 → 6.0）

第一轮的结论写在 Artifact 的「审计报告」里。**这一份写的是怎么做那一轮，以及
那一轮的方法在哪里失灵。**

## 1. 四条不要相信

第一轮踩到的，按代价排：

### 1.1 不要把「绿」当成「查过」

`pnpm guardrails` 打印 `Design System guardrails passed` 的同时，`check-design-system`
里有**四条检查是死的**——6 处字面量退格符让它们的正则永远匹配不上。

发现它靠的是 SonarCloud 报了个「控制字符」：**另一个工具、另一条完全无关的理由**。
换句话说是撞上的，不是查出来的。

> **守卫坏掉的表现，和它正常工作的表现，都是「绿」。**

对策：`pnpm test:guardrails`（变异测试）。审计**第一步**就跑它，在读任何守卫输出
之前——因为后面所有结论都建立在守卫说真话的前提上。

### 1.2 不要转述工具的结论

第一轮把一条 Sonar CRITICAL 原样写进了报告，理由还写反了（见
`docs/audit/known-false-positives.md`）。

工具给的是**信号**，不是结论。每条要写进报告的发现，都必须**自己看过那段代码**并
能说清：它错在哪、照它改会发生什么。说不清就不写。

### 1.3 不要把结构变成描述再从描述重建

三份文档的 CSS 是逐字节抽出来的，一字不差；导轨是照着理解重打的，组顺序整个反了。

> **顺序活不过摘要。**

对策：能复制就不要复述。要比对就写脚本比对（`check-doc-shape`），不要靠眼睛。

### 1.4 消费端报来的「根因在 DS」，先做对照组

2026-08-26 opera 报来一条：React 的 key 警告指着他们的 `page.tsx:231`，追进 DS 的
构建产物，看到 `Section` 用的是 `jsx` 而不是 `jsxs`，结论是「根因在 DS，改一个字符
就行」，并登记了技术债 TD-011。

链条讲得通，但结论是错的。三个对照组一跑就清楚（用例见当时的临时探针，结论已固化
成 `tests/setup.ts` 里的 key 守卫）：

| 对照组                                             | 结果         |
| -------------------------------------------------- | ------------ |
| `<Section>{a}{b}{c}</Section>` 静态多孩子          | **不报警**   |
| 中间层拼数组 → 交给 `Section`                      | 报警         |
| 中间层拼数组 → 交给**裸 `<div>`**（DS 完全不参与） | **同样报警** |
| 中间层改用带 key 的 Fragment → 交给 `Section`      | 不报警       |

裸 `<div>` 报的是同一条，所以跟 DS 无关。而第一行才是关键：**`Section` 内部对
children 用 `jsx` 并不会引发警告**——静态多孩子在外层 `jsxs(Section, …)` 那一步就
被标记成已校验了，内层再迭代一次不会重复报。

顺带一提，那个「一行修复」并不存在：源码里写的是 `{children}`，`jsx` / `jsxs` 由编译器
按调用点的字面孩子决定，没有哪一行可以改成 `jsxs`。

**为什么会查到 Section 头上**——因为 React 的警告原文点了两个名字，恰好都不是真凶：

```
Check the render method of `Section`.          ← 收下这个数组的件（DS 的）
It was passed a child from AccountDetailPage.  ← 元素被创建的地方（页面）
```

真正拼出无 key 数组的那一层（他们的 `DecisionChain`，DS 全仓没有这个名字）**一个字
都没被提到**。查的人顺着两个名字走，一个通向 DS，一个通向页面——于是绕开了中间层。

> **消费端说「根因在你这」时，先造一个不含 DS 的对照组。** 症状在对照组里照样出现，
> 讨论就结束了；照样不出现，才轮到看 DS 的实现。

最后一点判断：这条警告**不能压**。`[a, b].filter(Boolean)` 少一个成员时后面的会落到
前面的索引上，React 按索引复用实例——同类型的兄弟之间状态会串（实测点到 `B:3` 的
计数器在 A 消失后变回 `B:0`，它捡了 A 的那一格）。DS 若用 `Children.toArray` 之类
的手法把警告吃掉，就是把消费端的真缺陷盖住。DS 该做的是保证自己不出这个形状——
已落成 `tests/setup.ts` 里的 key 守卫，整套 189 条用例目前零警告。

## 3. 分类判据

按**缺陷是怎么逃过检查的**分，不按它在哪个文件——因为那才决定下一条同类缺陷会不会
再逃一次。第一轮分出四类，够用：

| 类                   | 特征                   | 典型                                 |
| -------------------- | ---------------------- | ------------------------------------ |
| 静默失败             | 构建全绿，只是结果不对 | 类名哑火、挡位用错、body 锁死        |
| 契约只写在散文里     | 判据成文但没有载体     | `danger` 只染色不设防、文案出口      |
| **守卫自己停止守卫** | 表现是「绿」           | 退格符死正则、扫描面被白名单缩小     |
| 分层与打包的隐性约束 | 约束只写在运行时行为里 | server 入口崩、引用环、`Omit` 不分配 |

新发现如果四类都装不下，先怀疑是分类不够，再考虑加一类——**类别的价值在于它能预测
下一条**，不在于把清单填满。

## 3.1 写行为测试的三条判据

搭基座时立刻踩到一次，值得写下来。

### 通过两次的测试等于没测

第一版「整页锁死回归」断言的是「关掉确认框后 body 干净」。它绿了——**把
`modal={false}` 改回 `modal` 之后它还是绿的**。实测确认 jsdom 重现不了那个残留：
真实故障依赖两个锁的竞争时序，而 jsdom 的同步事件派发把竞争抹平了。

> **每写一条回归测试，都要把缺陷放回去跑一次。** 不红，这条测试就是装饰。

改法：换一个能稳定分辨两版的断言。模态菜单一开就给 body 挂 `data-scroll-locked`，
非模态的不挂——于是断言「菜单单独开着时不上锁」。它钉的是**机制**（不上锁就没有
竞争），不是症状，注释里写明了这个区别。

### 变异不红，先查代码，别急着加断言

2026-08-26 铺 hooks 用例时撞到第二次，比上一条更值钱。

把 `exitFullscreen` 里的 `unlockScroll()` 删掉，「退出时还回滚动」那条**照样绿**。
第一反应是断言太松，想再加两句。往下追才发现不是测试的问题：那个标着
**「组件卸载时清理」** 的 effect，依赖数组里带着 `state.isFullscreen`——effect 的清理
**每次依赖变化都会跑**，不只是卸载。于是退出的那一帧它先跑了一遍清理，把
`exitFullscreen` 自己那次 unlockScroll 顶掉了。

顺带两个后果：原生模式下退出会**调两次** `exitNativeFullscreen()`；注释和代码说的
不是一回事，而注释是唯一能看出作者本意的东西。

> **变异测试留绿，有两种解释：测试没钉住，或者代码里有条多余的路在兜着。**
> 先分清是哪一种。直接补断言，等于把那条多余的路一起焊死。

改法是把清理 effect 做成真正的卸载时（空依赖 + 一个 ref 拿最新状态），`exitFullscreen`
里那次调用重新变成唯一的退出路径——这时两条变异（退出不还原、卸载不还原）才**各自
都能变红**，说明两条路是真的分开了。

### 测试不许逼守卫开口子

测试放在 `packages/design-ui/tests/` 而不是 `src/**/__tests__/`，因为 `src/` 下有两条
守卫在扫：`check-i18n-seam` 禁中日韩字符（而用例名是写给维护者的中文散文），
`check-preview-coverage` 要求 `components/` 下每个 `.tsx` 都有预览条目。

**为了迁就测试而给守卫开豁免，是把安全网剪个洞。** 挪个目录就没有这个问题。

## 4. 报告的硬要求

- **每条发现给出失败场景**：什么输入 → 什么错误结果。给不出就还没查清
- **写明是谁抓到的**：机器抓的写哪条守卫，人抓的写谁提的。第一轮两条最贵的发现
  都是消费侧评审提的，这件事必须写进报告，否则下一轮会高估机器
- **不写没验证的数字**。数字要带测法（见基线快照的 `how` 字段）
- **勘误留在原地**，不要把错的那段悄悄改掉——读者需要知道结论变过

## 5. 下一轮的已知缺口

**口径已经换过一次，先说为什么。** 前四轮铺用例是按「件名」排的——先出过事的件，再同族的件，最后模板。这个口径现在衰减了：全仓还有 410 个分支没跑过，其中 **240 条（59%）落在已经有用例的文件里**。按件名排会以为它们「测过了」。

同时推翻一条我自己说过、没验证的话：剩下的零覆盖文件「多半是薄封装」。**按行数成立，按分支不成立**——`MetricGrid` 4 行 24 分支，`PanelCard` 1 行 9 分支。而前四轮修掉的缺陷（Drawer 挡位失效、`MetricListCard` 与 `EntryCard` 的键盘陷阱、`FullscreenProvider` 的清理时机）**全是分支缺陷**。行数是错的风险代理。

### 5.1.1 第四批学到的：**「不给就不渲染那一层」要数元素，不要数文字**

结构族第一轮变异有 5 条留绿，**全是同一个形状**：断言写的是「文字不在」或「角色不在」，而把 `{action ? … : null}` 改成恒渲染之后，渲染出来的是一个**空壳** —— 既没有文字也没有角色，从内容上分辨不出。

而空壳有代价：它带着 `gap` 与 `self-end`，会在标题块旁留出一段说不清来路的空白。

> **这类分支一律数元素**（`root.children` 的长度），不数文字。

同一轮还撞到第二个形状：`aria-hidden` 的断言写成「页面里存在某个 `aria-hidden`」，**被内层 svg 自带的属性满足**，把外层那一层拿掉也不变红。断言要落在**那一层本身**上。

### 5.1.2 第五批学到的：**测试代码此前从来没被类型检查过**

`packages/design-ui/tsconfig.json` 的 `include` 只有 `src`。接上 `tests` 之后一次报出 11 条真错误，其中 5 条是**无效的图标名**（`gear` 不在词表里）——写在源码里会编译失败，写在用例里一路绿到底。

代价不是假绿：用例照样跑、照样通过。代价是**用例可以断言一个类型上根本不成立的用法**——那条断言测的是一个不存在的世界。

`tests` 现已纳入 `pnpm type-check`。

### 5.1.3 第五批学到的：`toContain` 是子串匹配

断言 className 时用 `expect(root.className).toContain("has-[…]:border-destructive")`——**删掉那条类之后照样绿**，因为 `dark:has-[…]:border-destructive/50` 仍然含这个子串。Tailwind 的变体天然让一条类成为另一条的子串。

> 断言 className **按 token 比**（`className.split(" ")`），不要 `toContain`。

### 5.1.4 一条没人验的理由，和一条从没生效过的守卫是同一类东西

`self-test.mjs` 里曾有一张「未做变异测试的守卫」表，三条各附一条理由。这张表在那里躺了一整轮，谁也没去验。**三条理由查下来两条不准、一条完全错：**

| 守卫                         | 表上写的                                                   | 实际                                                                                                             |
| ---------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `check-mode-blocks`          | 「任何单点变异都会同时改动两侧，造不出『只坏一边』的输入」 | **完全错**。删掉暗色块里一个变量声明就是只坏一边，守卫当场报「键集与默认块不一致——缺 1（background）」           |
| `check-server-entry-safety`  | 「变异源码后必须重新 build 才生效」                        | **不必**。它读的就是 `dist`，直接变异 `dist` 即可，17 秒                                                         |
| `check-packed-consumability` | 「同上，读的是 dist 与 pnpm pack 的产物」                  | 贵在 `npm pack` 不在 build；而且它还读**随包发出的 CSS 源文件**——改 `globals.css` 的 `@source` 就够，不用碰 dist |

三条的变异都已补上，**10 条守卫现在全部有变异用例**，没有跳过项。

> 这张表长得像已经想过了 —— 那正是它的危险处。**一条写下来没人验的理由，和一条从没生效过的守卫，坏的方式完全一样：都在「绿」里躲着。**

补的过程里还自己犯了一次同样的错：`check-packed-consumability` 第一次实测 140 秒，据此给它开了一条「慢车道」（默认跳过、只在 CI 跑）。量准之后拆掉了——140 秒是冷启动，稳定态 27~41 秒，全套自测带上它 66 秒、不带 48 秒。**差 18 秒撑不起一条会让人漏跑的分支。**
