审计报告

一套把判据从散文搬进机器的设计系统，以及它到今天为止仍然搬不动的那部分。覆盖 design-ui 3.2 → 6.0 一整轮，含四个 major。

01怎么查出来的方法

本报告里的每一条缺陷都真的发生过，来自 2026-08-25 一整轮从 design-ui 4.0 到 6.0 的开发与发布。分类不按「在哪个文件」，按它是怎么逃过检查的——因为那才决定下一条同类缺陷会不会再逃一次。

type-check 全绿、lint 全绿、构建全绿，并不能证明这套系统是对的。本报告里被机器抓到的那些，全部来自 pnpm guardrails 与 SonarCloud；而最重要的两条是人抓的——见结论。

03一类：静默失败最贵

没有任何东西报错，构建照样绿，只是结果不对。这一类在 DS 里格外多，因为 DS 的产物大量是「字符串」——类名、token 名、文案，写错的字符串不是语法错误。

类名哑火本轮抓到 1 处历史 130 处

DS 包用 tsup 打包，自身从不跑 Tailwind 编译。组件里写错或写了已退役的类名，包内 build 全绿、eslint 全绿、类型全绿——只在消费方渲染时无声失效：元素照样挂着那个 class，只是没有任何规则匹配。

本轮实例：给前置条件的说明文字写了 text-body-xs，而排版族的最小档是 text-body-sm，text-body-xs 根本不存在。

由 check-component-classes 抓到——它把 981 处类名逐个喂给真实的 Tailwind 编译器，看能不能产出规则。这条守卫存在的全部理由就是这类失效。

挡位用错，只是「看起来淡了一点」人眼在迁移时发现

预览面某个确认对话框的提交按钮写的是 variant="destructive"，而按 03 §3 落锤该用 destructive-strong。两个挡位都存在、都合法、都能编译——差别只是实心红与淡底红。

这类缺陷机器查不了：挡位选得对不对是语义判断，不是形状判断。

整页失去交互，只能刷新浏览器3.2.0 修复

Radix 的模态 DropdownMenu 与模态 Dialog 各自往 <body> 挂 pointer-events: none。菜单项 onSelect 里打开对话框时，菜单的解锁与对话框的加锁同拍竞争，对话框关闭后锁残留。

在 opera 模型服务页以真实鼠标事件复现（菜单 → 编辑 → 取消 → body 恒为 pointer-events: none）。页首按钮直开的对话框始终干净——锁死只发生在「菜单开出来的对话框」这条路上。没有任何静态检查能看见它。

进度条对读屏器永远是「正在忙」本轮发现 6.0.8 已修

Progress 把 value 从 props 里解构走之后，只拿它算填充位移，忘了传回 Radix 的 Root。屏幕上一切正常——色条画在 70% 的位置；语义上整条丢了：aria-valuenow 一次都没发出去，data-state 永远停在 indeterminate。

这是从上游 shadcn 照抄进来的 bug。本仓文件头写着「结构照 shadcn 官方 Progress」——那句话此前读起来是出处说明，现在它同时是一条线索：上游的缺陷会一并抄进来，而「照抄上游」通常被当作不必再审的理由。
「已认证」前面并排两个对勾本轮发现 9.0.8 已修

StatusBadge 的前导图标缺省就随语气来（它的文件头写着「不必每处各配一张」），success 语气自带圆形对勾。ShellUserMenu 在它之外又显式画了一个 check。

两条缺陷是同一个形状：「这件事已经有人做了，本件不知道」。都不报错、都不影响布局、都在看得见的地方躺了很久——读代码时那一行看起来都是对的（value 明明在用，check 明明该画）。要看出问题，得同时打开邻居的文件。

由此得到一条可复用的判据：组件调组件的地方，问一句「这件事被做过两遍，还是一遍都没做」——单看本文件永远答不上来。

04二类：契约只写在散文里最普遍

判据已经想清楚、已经写进文档，但没有载体——于是只有读过那一页文档的人写得出正确代码，读没读过没有任何反馈。

这一类是本轮四个 major 的共同起因。每一个 major 都在回答同一个问题：这条判据的形状在哪？
红色，但不设防4.0.0消费侧提出

ActionMenuItem.danger 曾是纯视觉开关：把菜单项染成 destructive 语义色，点了立刻生效。红色让运营以为「系统知道这很危险」，而系统其实什么都没做——视觉上警告、行为上不设防，凑在一起比不染红更危险。

而 03 §3 早就写了「真正的拦截交给二次确认，不靠按钮颜色吓人」，05 §46 早就把确认文案钉成三件套。两条都成文，两条都只活在散文里。

默认值也是反的：不写确认零成本，写确认要自己拼一整个对话框。

修法
收成判别联合：danger: true 必须给 confirm 或写明 confirmExempt 理由
为什么放类型不放守卫
check-* 的消费方那一半扫的是 portals/**，DS 仓没有这个目录、看不见任何调用点。lint 规则不跟着 npm 包走，类型跟着包走。
同一条散文，在 i18n 上重犯一次4.2.0 · 15 处 / 7 个件

DS 的约定不是「组件里写中文」，是「中文默认值 + 调用方可覆盖」——十几处 cancelLabel / placeholder 都守着它。但破这条约定不报任何错：把 aria-label="关闭" 直接写进 JSX，三种检查全绿，只在双语门户上线时变成一句改不掉的中文。

其中两处尤其能说明问题：DataTable 的「操作」是可见表头；BulkActionBar 的「已选择 {count} {noun}」把中文语序也焊了进去——只开 noun 一个口子，英文换不出 {count} {noun} selected 那句话。

语序是语法，不是词汇。只收词的件，看着有出口，实际换不了语言。

文档自己吹了牛4.0 写下 · 6.0 才真正补上

4.0 的更新日志与 03 §3 称 grep -rn confirmExempt 给出「本产品有多少个不设防的红色动作」的完整清单。这句是假的——判别联合当时只管两个数据驱动的件，够不到裸的 <Button variant="destructive">。

具体后果：accounts 删 passkey 的按钮（红色、不可逆、删的是安全凭据，删掉最后一个就把自己锁在外面）一直不设防，而那条 grep 会把 accounts 报成干净。

一份自称完整的清单，比没有清单更坏。4.1 的处置是把文档改诚实、给出两条 grep 的口径——那让文档对一个洞诚实，并没有把洞补上；而第二条 grep 是纯人工纪律、没有强制力，正是这套契约一开始要消灭的东西。

05三类：守卫自己停止守卫最危险

这一类失败的表现全都是「绿」。守卫还在跑、还在打勾，只是不再看该看的东西。指标因为覆盖面缩小而变好看，比指标难看危险得多——它把「没在看」伪装成「没问题」。
一条真实的供应链发现，被标成「已修复」本轮制造并修复

给仓库配 SonarCloud 时把 sonar.sources 写成白名单 packages,scripts，.github/ 随之离开扫描范围。SonarCloud 于是把那里一条真实发现直接关掉：

.github/actions/setup-node-pnpm/action.yml
Omitting --ignore-scripts allows lifecycle scripts to run during package install
→ 状态标成 FIXED

没人修过它。文件只是不再被看。项目 vulnerabilities 从 2 掉到 1、files 从 236 掉到 195，数字全线变好。

修法
扫全仓（sonar.sources=.），减法一律走 exclusions
判据
两种错的代价不对称：白名单式 sources 每加一个新顶层目录都要有人回来补一笔、漏补没有任何反馈；黑名单式 exclusions 漏补只是多扫一点噪声
六处退格符，让四条检查从写下那天起就没跑过建档时查到

check-design-system.mjs——DS 最大的那条守卫——里有 6 处字面量 U+0008（退格符），位置全都是本该写词边界的地方。含它的正则永远匹配不上：

L493
.vx-page-stack 选择器检查
L645 / L770
DS 收敛样式不许硬编码 motion 时长（两个路径集）
L2634
时长字面量判定的 helper

修回词边界后第一次跑就报出违规，进而查明规则自身还有第二个缺陷：两条 motion 规则用的 stripLineComment 只认行注释，而 DS 的样式叶子是 CSS、注释是块注释——于是撞上的两条全是解释性文字。规则在惩罚写清楚原因的人。两处一并修好后全绿。

病因是转义层被吃掉一层：经某些工具写文件时 "\b" 退化成 ""，后者在 JS 字符串里就是退格符。同一个坑在修这条的过程中又重现了三次——它不是一次手滑，是一类系统性故障，故落成 check-control-chars：除 tab/LF/CR 外源码里不许出现 C0 控制字符。这类字符在编辑器、diff、评审里全都不可见，唯一能看见它的是机器。

一行常量声明，让整个文件不再检查写守卫时踩到

新写的 check-i18n-seam 要跳过 DEFAULT_* 常量块，第一版用「独占一行的 ];」找收尾。而 const DEFAULT_PAGE_SIZES = ["auto", 10, 20, 50, 100]; 的收尾就在声明行上，匹配不到——inDefaults 再没被关掉，从那一行起整个文件不再检查。

改成按括号深度算，单行声明当场归零。

正则分不开的两种东西同一条守卫，第二个坑
ariaLabel="每页条数"
JSX 属性——写死的文案
ariaLabel = "每页条数"
形参默认值——可覆盖

在正则眼里没有区别。靠「形参默认值必然以逗号收尾、JSX 属性不带」才分得开——少了这条，Pagination 那两处从头到尾没被报过。

一个汉字都没有的中文扫描范围定错

titleTemplate = "{verb}{target}？" 里没有任何汉字，只有一个全角问号（U+FF1F，不在 \u4e00-\u9fff 区间）。而它正是「件替调用方决定语序」那条缺陷的残留——只扫汉字的那一版守卫从头到尾没报过它。

扫描范围补上 CJK 标点与全角形式后当场报出。

三份 walk，改规则要记得改三处SonarCloud 抓到

三个守卫各写了一份目录遍历，彼此只差一个扩展名过滤。漏改的那一处不会报错，只会少扫一些文件——又是一次守卫静默缩小覆盖面。已抽成 lib/collect-files.mjs。

本轮之后，这条守卫的判据换成了二值的：剥掉注释后不许出现中日韩字符或全角标点。没有启发式，就没有误判，也不存在「看起来在查其实没查」的中间态。脚本从 151 行缩到 60 行。
一整类文件从来没被格式检查过本轮发现 已修

format:check 的 glob 是 **/*.{js,ts,tsx,json,md} —— 没有 mjs。而 scripts/ 几乎全是 .mjs：十条守卫、令牌生成器、审计快照、守卫自测，一个都不在检查范围里。

是在给快照脚本补一行时撞见的——那一行 prettier 说不合规，而它两周前就写进去了，一路绿到当天。实测 27 个 .mjs/.cjs 里 16 个有真实格式差异。

一条检查的「覆盖面」和它的「判据」一样重要。判据写错了会报假绿；覆盖面漏了一整类文件，则连绿都不报——它根本没看那边。这与本节第一条（扫描面被白名单缩小）是同一个形状，只是这次漏的不是目录而是扩展名。
一个恒红的检查，同样什么都没查本轮发现 已修

本机 pnpm format:check 恒红：112 个文本文件是 CRLF，其中 89 个落在 glob 内，全部报「不合格式」——而它们的内容一个字都没错。根因是仓里没有 .gitattributes，检出行尾由各人机器上的 core.autocrlf 决定；CI 跑在 Linux 上、检出就是 LF，所以从没在 CI 上现形。

恒红比恒绿更费时间：它每次都要求你重新说服自己「这次也是行尾问题」，而真出现一次格式问题时没人分得出来。

两者的处置相反：恒绿要补变异测试去戳穿它，恒红要去掉那个恒定项，让它重新变成信号。已补 .gitattributes（* text=auto eol=lf），CRLF 文件 112 → 0。

06四类：分层与打包的隐性约束最容易踩

这一类不是逻辑写错，是把一件正确的东西放错了层。共同点：约束不写在任何一份文档里，只写在打包器和运行时的行为里。

能弹模态的 base 原语，就不是 base 原语6.0 设计推翻重来

原计划让 base 的 Button 直接收 confirm 并自己弹确认框。做完之后守卫报红：

✗ @vxture/design-ui 的 /server 入口在 react-server 下求值失败：
React.createContext is not a function

MetricCard 在 server-safe 名单里且引了 Button，于是 Button → ConfirmDestructive → AlertDialog 把 Radix 的 createContext 拖进了 /server 入口。

改成：base 的 Button 只承担类型义务（variant="destructive" 必须写 confirmExempt），拦截交给 composite 的 DestructiveButton。与 Dialog → DialogForm 同一步棋——原语只管形状，契约由组合件承担。

今天绿、明天红的引用环同一次设计中发现

Button → ConfirmDestructive → AlertDialog → Button。ESM 能加载循环，但 const 导出会撞上 TDZ，而撞不撞取决于打包器的模块顺序——这类故障不会在开发机稳定复现。

Omit 在联合上不分配，于是有了后门这个坑不报错

ActionButton 用 Omit<ButtonProps, "children"> 透传。ButtonProps 变成判别联合之后，TS 会先把分支并成一个「什么都可选」的对象再删键，variant 与 confirmExempt 的绑定关系当场丢失。

结果是 ActionButton 成了绕开确认契约的后门，而且是静默的。换成 DistributiveOmit 后契约恢复，已加编译自检钉住。

数据平表被判成重复代码质量门拦截

把 14 个图标分组名改英文后，那 14 行成了「新增行」，落进本来就存在的重复块里，PR 的新增重复率冲到 92.9%。重复早就在——图标字典是一张平表，14 个 { label, icons: [...] } 结构相同内容不同。给一张数据表发明抽象只会更难读，故走 sonar.cpd.exclusions，只关重复这一项。

07覆盖面盘点十一条守卫

每条守卫补的是一个具体盲区。判断一条守卫值不值，看的是它抓到过什么真东西，而不是它跑得多快。

守卫补的盲区抓到过
check-design-system包依赖方向、token 桥、消费方用法双管辖；本仓只跑得到 DS 自身那一半
check-component-classes类名哑火——tsup 不跑 Tailwind，写错的类名全绿是 本轮 text-body-xs；历史 130 处
check-design-system-exports公开入口悄悄增删是 每次新增导出都要显式确认版本影响
check-preview-coverage组件加了没人回来加预览条目是 曾有 17 个组件不在预览面上
check-i18n-seam文案写死、调用方覆盖不掉是 15 处 / 7 个件
check-server-entry-safety/server 入口在 react-server 下不可求值是 本轮拦下 Button 弹模态的设计
check-packed-consumability发布产物装到消费方就哑（@source 覆盖）持续守着 17 个产物文件
check-control-chars源码字节里的不可见字符是 6 处退格符，让 4 条检查静默失效
check-mode-blocks明暗 / 密度 / 字号三轴键集漂移持续守着三族模式块
check-doc-shape文档结构被凭记忆重打（导轨顺序、组名）是 建档当轮就抓到导轨整个反序、一个组被改名
机器守得住
  • 形状对不对：类名存不存在、导出面变没变、键集齐不齐
  • 产物装不装得上：打包边界、server 求值、@source 覆盖
  • 生成物与策略源同步：11 个 token 脚本的 --check 模式
  • 类型层的契约：判别联合把「红必带拦」变成编译错误
机器守不住
  • 形状够不够：出口开了，但只收词不收模板，语言还是换不掉
  • 挡位选得对不对：destructive 与 destructive-strong 都合法
  • 契约覆盖全不全：本轮最大的一个洞正是「少了第三个载体」
  • 运行时行为：已补 189 条用例，但仍有 410 个分支没跑过——其中 59% 在已经有用例的文件里

09结论这一轮学到的

本轮两条最重要的发现，都不是机器抓的。「红色但不设防」和「契约漏了第三个载体」，都由消费侧评审提出；后者还提了两次——第一次被我用一条站不住的理由挡了回去。
判据必须有载体

一条判据写进文档、没有载体，等于只对读过那一页的人生效。本轮四个 major 全部在回答同一个问题：这条判据的形状在哪？放进类型（判别联合）、放进守卫（二值判据）、放进生成脚本（--check）——三种载体，共同点是写错会有反馈。

类型跟着包走，lint 不跟着

DS 仓的守卫看不见消费方的调用点。要在 opera 的编译期拦住「红色但不设防」，判据只能放类型。这条决定了本轮所有契约都收成判别联合，而不是新增几条 lint 规则。

指标变好看要先问覆盖面

vulnerabilities 从 2 掉到 1 那一次，是覆盖面缩小而不是问题解决。守卫静默停止守卫，比没有守卫更坏——本轮栽了两次（sonar 白名单、单行常量打穿常量块追踪），两次的表现都是「绿」。

豁免要可清点

confirmExempt 收字符串而不是布尔，是为了让「本产品有多少个不设防的红色动作」变成一条 grep。清单比错误有用——但前提是清单完整，不完整的清单比没有清单更坏。

变异不红，先查代码补记于四轮之后

给回归测试做变异时有一条没变红。第一反应是断言太松，想补两句。追下去发现不是——FullscreenProvider 里那个标着「组件卸载时清理」的 effect 依赖数组带着 state.isFullscreen，每次进出全屏都在跑清理，把 exitFullscreen 自己那次调用顶掉了。留绿有两种解释：测试没钉住，或者代码里有条多余的路在兜着。直接补断言，等于把那条多余的路一起焊死。

别人说「根因在你这」，先做对照组补记于四轮之后

消费端报来一条 React key 警告，归因到 Section 内部用了 jsx 而非 jsxs，「DS 改一个字符即可」。把 Section 换成裸 <div>——报的是同一条，与 DS 无关。真凶是中间层拼出的无 key 数组，而 React 警告点的两个名字恰好都不是它。造一个不含 DS 的对照组，比读三层调用链快。

四轮之后，这份报告的口径该换了。初审问的是「形状对不对」——类名存不存在、导出面变没变、键集齐不齐，机器都能答。补完测试之后能问「行为对不对」，但能问不等于问过：410 个分支没跑过，59% 在已经有用例的文件里。下一轮的清单不再按件名排，按未覆盖分支排。
