01怎么查出来的方法

下面每一条都是真的发生过的缺陷，来自批次 10–14 的开发。它们的共同点比内容更重要：

类型检查、单元测试、生产构建三者全绿，并不能证明功能可用。本报告里没有一条是被这三样抓到的——全部由「拿真实数据库把流程点一遍」抓到。
走查方法已固化为习惯
为什么必须连真库
karda 的离线存储是每请求新建的——getKbStore() 每次返回 new InMemoryKbStore()，所以离线点一遍几乎什么都证明不了

查什么
把该批次的验收标准当作剧本走完，而不是逐个点按钮

02一类：静默失败最贵

最贵的一类：没有任何东西报错，界面还回报成功。

验证策略从来就存不进去批次 11 发现

KbService.update 的运行时白名单漏了 defaultVerifier 与 defaultVerifyIntervalDays。路由读了它们，service 丢掉，界面报成功。

连锁后果：没有间隔就没有内容会到期 → 续验扫描永远无事可做 → 待复验队列永远填不满。批次 11 的整个前提压在一次静默没发生的写入上。

已修：白名单补齐，并加测试逐键钉住往返——白名单里少一个键是静默丢失，不是报错，所以必须由测试覆盖。

信封 key 写错 → undefined 进状态批次 10 发现

某个 PATCH 读 kb，而所有 kb 路由发的是 knowledgeBase。req<T> 是裸类型转换，写错不是错误——它是 undefined，进了页面状态，几次渲染之后在一张与该请求无关的卡片上崩溃。

已修：加 need() 在 fetch 边界失败，并报出端点与 key；17 个单对象 helper 全接上。

上传从不携带 folder_id批次 10 发现

路由从一开始就在读 folder_id，但客户端从来没发过——所以不管用户在哪个目录里操作，文件一律落到「未归档」。没有报错，只是永远归错档。

03二类：整条能力对中文失明最严重

在一个中文优先的产品里，唯一在跑的召回器把中文全部丢弃。
BM25 分词器只匹配 [a-z0-9]+批次 13 发现
实测
tokenize("小雨条件下单架次时长为 25 分钟") → ["25"]
tokenize("小雨 单架次 时长") → []

这不是「中文排序差一点」——中文查询产生零个 token，对中文内容零命中。而当时 BM25 是唯一在跑的召回器（向量召回还等 Atlas A1）。karda 整条能用的检索链路对中文是瞎的。

注释里写着「Good enough for v1」——那句话是按英文假设写的，而这个假设在这里不成立。

已修：CJK 重叠二元组（Lucene CJK 分析器的做法）。单架次时长 → 单架/架次/次时/时长，查 单架次 靠 单架+架次 命中，不需要分词词典。刻意不用词切分：词典是依赖、要维护，而且恰恰在 karda 面向的技术语料里最容易切错。不需要重建索引——排序是查询时从存储文本现算的。

它是怎么被发现的：检验台（批次 13 建的那个界面）本身就是为了让人能判断「karda 会不会给我的 agent 好答案」。第一次拿真实中文内容去问它，答案是不会。这个界面存在的意义就是这个。

04三类：公布了却没兑现契约违约

公布在契约里、调用方按它编程、而实现从来没兑现的东西。

karda.ask 接受 verification_filter 然后丢掉批次 13 发现

karda.ask 在工具描述符的输入清单里公布了 verification_filter，MCP 通道也把它传下来，而 ask-tool 从来没读过——runAsk 调 runSearch 时根本不传 params，于是每次问答都悄悄回落到默认档。

后果：Agent 要 verified_only，拿到的引用里混着它明确排除掉的未纳管内容——被当作依据引回给它。在一个带引用问答的产品里，这是承诺被破坏，不是功能缺失。

已修：接通，并把系数转换收成一份共享模块（原本两份一模一样的副本，而 ask-tool 一份都没有——那正是它被漏掉的原因）。

05四类：看着能操作，其实是死路

界面摆出一个操作，而它必然失败或通向空白。比没有这个操作更糟。

低于覆盖基线的列表混入未开治理的库批次 11 发现

未开验证治理的库，里面的东西根本没法验证，但它以 0% 高踞「接下来看这里」列表首位。点进去是空队列。已从列表剔除；覆盖率分母保留不动——改分母等于改口径，那是 owner 的决定（后来定为 KD-208）。

撤销的真正后果没人说批次 12 发现

uidx_binding_kb_connector_source 对三元组唯一且没有 state 谓词，而 findBySource 连 revoked 行也匹配——所以一个来源从某个库撤销后，永远无法再绑回该库。

API 里没有任何地方说这件事。点完才知道就太晚了。现在确认框在点击之前说清：多少份文档退出检索、其中多少份是已验证的、以及该标识已被永久占用。

DS DialogTitle 高度为零批次 10 发现 · 影响所有消费方

DS 的 DialogTitle 自带 leading-none，在 Tailwind v4 + DS token 下解析为 line-height: 0（leading-* 回退到 --spacing-*，而 DS 注册了 --spacing-none: 0px）。

它能过类型、在 DOM 里、读屏也正确——只有截图能看见它不在。而且 grep 自己的源码找不到：类名在 DS 包里。已上报 vxture-design#8，本地 leading-[1] 兜住，记 TD-013。

06五类：环境缺件，表现得像产品缺陷

不是产品缺陷，但表现得一模一样——这类最容易被误判。

上传的字节被丢弃2026-08-25 发现

KARDA_OBJECT_ROOT 在 dev 栈里没配，对象存储回落到内存实现，而它是每请求新建的。上传当场返回 201，之后每次预览/下载都 object_missing。批次 10 的主打功能在这套栈上从头就是坏的，而看起来像是预览功能写错了。

光加环境变量还不够：Docker 用镜像里那个目录（含属主）初始化新的命名卷，镜像从没创建过这个路径，卷就落成 root 属主，而运行用户是 nextjs。所以 Dockerfile 里建目录并 chown，compose 挂命名卷。

dev 库的 schema 停在批次 9 之前2026-08-25 发现

processing_task 等四张表根本不存在——apply-local-dev.sh 从批次 9 之后就没再跑过。供给通道的消费方下钻在补表前必然 500。脚本是幂等的，补一次就好；问题在于没有任何东西提醒它该跑了。

看的端口在服务旧镜像2026-08-25 发现

3240 被容器占着，跑的是构建好的镜像而非工作区代码，所以批次 10–13 的改动一个都不在里面——而这看起来就像「做了但没生效」。compose 文件开头就写着它从工作区构建；重建镜像即可。

07仍然开着的

知道、但有意没修的。

项状态为什么
DS DialogTitle 零高上游TD-013 / vxture-design#8。本地已兜住；真正的修法是在 tokens 里注册 --leading-none: 1，一次修好所有消费方
验证历史口径已澄清三个列只存最近一次验证。真历史需要 append-only 台账——也是企业档 governance.audit 要的东西
管家预验队列有意不建背后没有台账。先建 UI 会让演示数字看起来可操作
评测 API 的连接器降级路径无实跑注册表里只有一个连接器，且是能力最强的声明，所以降级与 I4 缺口的渲染路径没跑过；已用投影层单测钉住最弱能力组合
部署流水线未演练已编写；模板里端到端跑通过，karda 这份还没有

08结论

这些缺陷没有一条是被类型检查、单元测试或生产构建抓到的。它们全部由「拿真实数据库把验收标准走一遍」抓到。

为什么会这样，值得说清楚：

  • 类型系统检查形状，不检查语义。白名单漏一个键、信封 key 写错、分词器丢掉一整个字符集——三者都是类型完全正确的代码。
  • 单元测试测的是被测到的东西。没有人会为「路由读了但 service 丢了」写测试，因为写测试的人以为它接通了。
  • 渲染成功不等于可见。零高度的标题在 DOM 里、在读屏里都是对的。
  • 离线路径会掩盖问题。每请求新建的内存存储让上传「成功」、让数据「消失」，两件事都不报错。
已固化为习惯：每批次交付前，起一次性 Postgres，按验收标准把流程走完，再清理环境。批次 10–14 每一批都是这样收的口，本报告里的每一条也都是这样来的。
