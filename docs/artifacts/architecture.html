系统架构

三个包、四层件、两条硬边界。每一条边界都对应一次真实的故障——本页把边界和它的病因写在一起，因为脱离病因的规矩会被下一个人当成洁癖删掉。

01三包怎么分职责

@vxture/design-tokens
取值。T1 原子层镜像 Tailwind，T2 语义层是产品面。全部由脚本生成并入仓。
▸
@vxture/design-ui
无状态的件。96 个件，只认形状不认业务。不含任何 provider。
▸
@vxture/design-system
伞包 + 运行时接线：主题 / 密度 / 字号 provider、shell、品牌样式入口。应用侧主依赖。
包版本装什么谁装它
design-tokens2.2.3CSS 变量两层 + z 阶梯/密度/字号的 TS 面只被上面两个包装
design-ui6.0.8组件、图标、recipes、hooks被伞包装
design-system9.0.8把两包原样转发 + 自持的 provider / shell / 样式入口五个门户
design-preview私有预览面。这套系统唯一的验收面不发布
应用只装伞包。直接装 design-ui 就拿不到运行时接线（主题/密度/字号 provider），且版本约束不再由伞包保证——伞包对另两包钉的是精确版本而不是 caret，因为它把两包的类型原样 re-export，caret 允许消费方解析到与伞包构建时不同的次版本，在转发边界上产生类型不匹配，而这类不匹配在伞包自己的 CI 里看不见。

02依赖方向单向，无环

包与包之间是单向的，件与件之间也是。后者没有守卫，只有约定——而 6.0 的设计正是被它拦回来的。

今天绿、明天红的引用环6.0 遇到

让 base 的 Button 引 ConfirmDestructive 时出现过 Button → ConfirmDestructive → AlertDialog → Button。ESM 能加载循环，但 const 导出会撞上 TDZ，而撞不撞取决于打包器的模块顺序——这类故障不会在开发机稳定复现。

解法有两种：把共用的叶子（buttonVariants）拆成独立模块，或者让上层不引下层。6.0 选了后者——因为环只是症状，base 引 composite 本身就是方向错了。

03件的四层96 个

层数量判据可以引
base50一个控件、一个交互单元；或由 Radix 原语换取值而来tokens、recipes、icons
composite29由 base 单件拼装、零业务、直接给 props 可用base、同层
templates / layout12整页骨架与布局容器base、composite
shell（伞包自持）6需要运行时接线的：主题、密度、导航壳全部下层
「由 base 单件拼装」正是 composite 的定义，不是它可以下沉到 base 的理由。6.0 时我把 ConfirmDestructive 挪进 base/overlay/，理由是「它的依赖全在 base」——这句话恰恰说反了：依赖全在 base，说明它是 composite。后来挪了回去。

04两条硬边界收件门槛

零业务

组合件只认形状不认业务含义——DataTable 有列定义，没有「租户列表」。带业务归属的面板（UserPanel / TenantPanel 一类）不进本包。

tone.ts 是这条边界最锋利的一处：六档语气只表达严重度，不表达业务状态。这里没有 overdue / suspended——把「订阅逾期」映射成 warning 是产品的判断，不同产品对同一状态的严重度本就可以不同。

不带产品专名

没有 console-* / admin-* / platform-* 前缀。一个件如果只有一个产品用得上，它就还没到进 DS 的时候——收录门槛是产品实据：得先在多个消费方里被各自重写过。

这条边界在本轮被反复用来做判断，而且两次结论相反。「前置条件三态」是形状问题（Checkbox 的半选态早就承认「布尔说不出的第三态」），收；「读不到检查单时挡住还是放行」是产品的风险判断，不收。同一个件里，一半收一半不收——边界是画在字段上的，不是画在件上的。

05server / client 边界最容易踩

两包各有一个 /server 子入口，收的是能在 React Server Component 里直接用的那一小撮件。判据极严：整条 import 图只能是 react + utils/cn（或名单里的其他纯叶子）。

入口导出数不许出现
design-ui/server19任何 hook、任何 Radix、任何 icons（图标注册表在模块加载时调 createContext）、任何 context provider
design-system/server27
能弹模态的 base 原语，就不是 base 原语6.0 设计被推翻

原计划让 base 的 Button 收 confirm 并自己弹确认框。守卫当场报红：

✗ @vxture/design-ui 的 /server 入口在 react-server 下求值失败：
React.createContext is not a function

MetricCard 在 server-safe 名单里且引了 Button，于是 Button → ConfirmDestructive → AlertDialog 把 Radix 的 createContext 拖进了 /server 入口。

这条边界不写在任何一份规范里，只写在运行时的行为里——所以它必须有守卫（check-server-entry-safety 会把 dist 的 server 入口放进 react-server 条件里真的求值一遍）。

06token 链路生成物入仓

策略源
*-policy.mjs：偏离登记、色板、排版刻度
▸
generate-*
T1 原子层
21 文件 / 247 项。镜像 Tailwind theme，偏离逐条登记
▸
T2 语义层
色彩 light/dark 各 132；排版 21 角色 × 3 档；间距 29 × 3 档
▸
@theme
工具类
Tailwind v4 注册，消费方直接写 bg-primary
生成物为什么入仓
事实
37 个生成文件全部提交进仓（T1/T2 的 CSS、theme.css、伞包的具名再导出、z/密度/字号的 TS 面）
为什么
CI 里没有任何步骤会重新生成它们。不入仓，type-check 就找不到模块
怎么防漂移
每个生成脚本都有 --check 模式，逐字节对账；进 pnpm guardrails
代价
对生成物报 code smell 是无处可改的噪声（唯一改法是改生成器），故 Sonar 排除这 37 个文件——但生成器本身在扫描范围内
token 的删改一律按 major。删掉一个 CSS 变量不会报错，只会静默失效——不做「应该没人用」的推定。这条判据后来被推广到了行为层：5.0 把默认文案从中文改成英文托底，类型一个字段都没动、不会编译失败，但每个消费方的界面都会变，同样按 major。

07构建与发布顺序是硬约束

1 · design-tokens
先建，另两包的取值来源
▸
2 · design-ui
tsup 打包；伞包的类型依赖它的产物
▸
3 · design-system
先跑具名再导出生成，再 tsup
顺序不是习惯，是硬约束。pnpm 打包时把 workspace: 协议替换成真实版本号，所以 design-ui 发出去会声明 "@vxture/design-tokens": "^x.y.z"。若那一版还没进 registry，消费方 install 直接失败，而流水线自己是绿的——pnpm publish 不校验依赖可解析。
为什么伞包要生成具名再导出而不是 export *

伞包产物被注入 "use client"，而对 external 包的 export * 会原样留在产物里——Next 15 的 next-flight-loader 在 server/client 边界上硬拒这个组合（它无法静态枚举客户端引用图）。修法就是错误信息里那句 Please use named exports instead：值走生成的具名清单（284 个），类型走 export type *（编译期擦除，无运行时痕迹）。

发布走 tag，且推 tag 就是发版没有第二道确认
流程
分支 → PR → CI → squash merge → 在同一 commit 上 dry run → 打 ds-v<伞包版本> → 推
tag 名规
三包版本各自独立，tag 名只能取一个，取伞包——消费方钉的就是它。完整三包版本写进 annotated tag 的注释
机制陷阱
DRY_RUN 取的是 github.event.inputs.dry_run，tag 推送时它是空的 → 直接真实发布。打 tag 前必须已在同一 commit 完成 dry run
幂等
每包各自判断该版本是否已存在，已存在即跳过；同一个 tag 重跑安全

08守卫布点十一条

每条守卫补一个具体盲区，头注释写明「补的是哪个盲区」与「实测抓到过什么」。那段注释是它存在的理由——删了它，这条守卫就没人知道为什么不能删。

守卫守在哪一层判据形态
check-doc-version文档 → 发布12 份文档声称的 DS 版本 == 伞包实际版本
check-design-system包依赖方向 · token 桥 · 消费方用法规则集，双管辖
check-component-classes组件 → Tailwind把 982 处类名喂真实编译器
check-mode-blockstoken 的明暗/密度/字号三轴块顺序 · 特异性 · 键集一致
check-design-system-exports公开入口快照对账，变化必须显式确认
check-server-entry-safetyserver / client 边界在 react-server 条件下真的求值
check-packed-consumability发布产物 → 消费方@source 覆盖 · 类型面 == 运行时面
check-preview-coverage件 → 预览面每个件必须有条目，排除要写理由
check-i18n-seam文案二值：源码里不许出现中日韩字符
check-control-chars源码字节二值：不许出现游离 C0 控制字符
check-doc-shape文档 → 底本导轨组、顺序、组名逐项比对
最后两条是二值判据，这不是巧合。启发式判据会误判，而误判会让人开始忽略这条守卫；更糟的是它会制造「看起来在查其实没查」的中间态——本仓两次栽在这上面（sonar 白名单把 .github 扫没了；一行单行常量声明打穿常量块追踪）。能设计成二值的，就不要留启发式。
守卫也会坏，而且坏了是「绿」2026-08-25 查到

check-design-system.mjs 里曾有 6 处字面量 U+0008（退格符），位置全是本该写词边界的地方——含它的正则永远匹配不上，四条检查从写下那天起就在打勾、什么都没查。修回词边界后第一次跑就报出真违规。病因是转义层被吃掉一层。check-control-chars 就是为这一类落成的。
