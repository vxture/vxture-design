接口文档

三个包的公开面：入口按读法切，不按功能切。四种调用者各读一个入口，而真正硬的那一半不在导出清单里——在判别联合。

01谁在读这个面四种调用者

公开面不是一份清单，是四种不同的读法。同一个 Badge，应用直接 import，server 组件要它不带 createContext，构建要它的类名进得了 Tailwind 的扫描范围，主题脚本则要在 React 还没接管之前就能跑。入口是按读法切的，不是按功能切的。

调用者读哪个入口它要的是什么
应用代码@vxture/design-system284 个具名导出，件 + provider + shell
server 组件@vxture/design-system/server27 个——在 react-server 条件下真的求值得出来
非 React 场合…/tokens7 个纯数据：z 阶梯、密度、字号、主题常量
只要类型…/types0 个运行时导出——它是 export type *
构建 / 样式5 条 CSS 子路径token 两层、品牌、字体、工作台
应用只装伞包。直接装 @vxture/design-ui 拿不到运行时接线（主题 / 密度 / 字号 provider），且版本约束不再由伞包保证——伞包对另两包钉的是精确版本而非 caret：它把两包的类型原样 re-export，caret 允许消费方解析到与伞包构建时不同的次版本，在转发边界上产生类型不匹配，而这类不匹配在伞包自己的 CI 里看不见。

这 284 个数字本身是一条守卫。check-design-system-exports 拿它与快照对账——增删导出必须显式确认版本影响，而不是等消费方装上才发现少了个件。快照里连 files 与 peerDependencies 一起钉住：漏掉 src/styles 的那一版，CSS 子路径会在消费方那边 404，而流水线自己全绿。

03server 子集27 个 · 边界不是约定，是断言

Next 的 server 组件在 react-server 条件下求值，那里没有 createContext。一个件只要在依赖链上碰到 Radix 的 context，整个入口就崩。

✗ @vxture/design-ui 的 /server 入口在 react-server 下求值失败：
  React.createContext is not a function

这不是假想——6.0 设计契约时，第一版让 base 的 Button 直接收 confirm 并自己弹框，守卫当场报红：MetricCard 在 server-safe 名单里且引了 Button，于是 Button → ConfirmDestructive → AlertDialog 把 createContext 拖了进来。一个能弹模态的 base 原语就不是 base 原语。

守卫怎么验

check-server-entry-safety 在 react-server 导出条件下真的 import 一次已构建的 dist，不是读源码猜。check-packed-consumability 再验一条：类型面 == 运行时面（design-ui 19 个、伞包 27 个）。两者不等意味着有个导出「类型上有、运行时没有」——消费方写得出来、跑不起来。

这个名单为什么这么短

能进来的只有不需要状态的件：卡、标、空态、栅格、版式容器。任何要 provider、要浮层、要事件的件都进不来——不是没做，是它们在 server 上本来就没有意义。要交互就用 client 组件从主入口引。

04纯数据与纯类型tokens · types

./tokens7 个，不含 React

DENSITIES        compact / default / comfortable
FONT_SIZES       small / default / large
THEME_CONSTANTS  主题的存储键与属性名
PREFERENCE_CONSTANTS
densityClass     档位 → 类名
fontSizeClass

给的是不需要渲染就要用到的东西：middleware 里读主题偏好、脚本里算层叠、测试里遍历全部档位。从主入口引这些会把整个组件库拖进去。

./types0 个运行时导出

这个 0 不是漏了，是它的定义：

export type * from "@vxture/design-ui";

export type * 编译后什么都不剩——所以运行时面是空的，而类型面是全的。给的是「只要类型标注、一个字节的运行时代码都不想要」的场合：类型声明文件、纯类型的工具包、server 边界上的签名。

导出快照把它记成 0 也是有意的——哪天它不是 0 了，说明有人往里塞了值，守卫会红。

05CSS 子路径五条 + tokens 两条

CSS 走的是 src/ 而不是 dist/——它不需要编译，而且必须让消费方的 Tailwind 扫得到里面的类名。

子路径装什么什么时候引
design-system/styles/globals.css总入口：串起 token 两层 + @source 指向必引，一次
design-system/styles/fonts.css字体声明用自带字体时
design-system/styles/brand.css品牌层入口要品牌色时
design-system/styles/brands/vxture.cssvxture 这一套品牌值由 brand.css 引
design-system/styles/workbench.css工作台专用版式只有工作台类页面
design-tokens/styles/tokens.cssT1 + T2 两层变量由 globals.css 引
design-tokens/styles/tailwind.css把 token 接进 Tailwind 的 @theme由 globals.css 引
@source 是这里最容易静默失效的一处。tsup 不跑 Tailwind——DS 的类名不在消费方的扫描范围里就不会被生成，件渲染出来没有样式，而没有任何报错。globals.css 里的 @source 指向 DS 的 dist，check-packed-consumability 每次验它是否还指得中（当前覆盖 17 个产物文件），并抽查 bg-primary / h-control-lg / shadow-raised 这类类名是否真的扫得到。
@source 必须排在所有 @import 之后。CSS 规范只允许 @charset 与 @layer 领先于 @import。这份文件是公开子路径、会进别人的构建，位置错了在消费方那边才炸。审计时这里报过三处，已修。

06类型契约这才是接口的硬的那一半

导出清单说的是「有什么」，判别联合说的是「不许怎么用」。DS 仓的守卫看不见消费方的调用点——要在你的编译期拦住误用，判据只能放类型。

红必带拦ButtonProps
// 不拦：必须写明为什么
<Button variant="destructive"
        confirmExempt="确认在流程第二步" />

// 要拦：换成 composite 的那一个
<DestructiveButton confirm={{ … }} />

没有第三种写法能过 tsc。ActionButton 透传 ButtonProps 自动跟着收紧——它的 Omit 换成了 DistributiveOmit，否则 TS 会把联合分支先并成一个「什么都可选」的对象再删键，绑定关系当场丢失。

同一判据的另外两个载体
ActionMenuItem
danger: true 必须带 confirm 或豁免
BulkActionBarItem
同上
为什么要三个
少一个就有绕路。4.0 只收了前两个，裸的 <Button variant="destructive"> 一直在洞里——而 grep confirmExempt 会把只有裸红按钮的产品报成「干净」。不完整的清单比没有清单更坏
DestructivePrecondition前置条件的形状
{ label: string; met: boolean; unknown?: boolean; note?: string }

met 是唯一的闸门，unknown 只影响显示。这是有意的：「查不出来算不算通过」是风险策略，属于产品。有的产品要求查不出来就拦，有的允许放行并记一笔——DS 收下这个判断就等于把业务语义焊了进来。

清点口径是一条 grep：grep -rn confirmExempt portals/。它完整，是因为剩下的情况编译不过。读的时候读理由本身——收字符串不收布尔就是为了让这份清单可以被人评审：「确认在流程第二步」是个理由，"ok" 不是。

07什么算破坏性版本口径

变更tokensuisystem
修 token 取值（不增删名字）Patch不变Patch
增 token 语义名 / 扩展档Minor不变Minor
删除或改名 token / 收窄色板Major视情况Major
修组件样式或行为 bug不变PatchPatch
新增组件、新增 cva 变体不变MinorMinor
删除或改名组件、改组件 props不变MajorMajor
删除或改名任一包的公开入口——Major
仅文档、CI、发布流程不发版
token 的删改一律 major

删掉一个 CSS 变量不会报错，只会静默失效。没有编译期能接住它——所以这里不做「应该没人用」的推定。这条与代码层的判据不同，是因为载体不同。

下层 major 向上传导

tokens 删一个名字，ui 的组件可能哑火，伞包的公开行为随之改变——所以下层 major 时上层同样按 major 处理，除非能证明变更未穿透。伞包用精确版本，这一点无法靠版本范围回避。

预发布的通道即标识符。2.0.0-alpha.0 发到 dist-tag alpha，不发到 latest——这条由流水线从版本号自动推出。pnpm publish 不带 --tag 一律打 latest，预发布版也不例外，漏了这一步等于把未完成的 major 推给了所有按默认范围安装的消费方。预发布期间请显式钉版本，不用 caret。
