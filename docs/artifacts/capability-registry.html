02带契约的件不只是形状

大多数件只固定形状。下面这几件还固定「必须做什么」——它们的类型会在你漏掉一步时编译失败。这是本轮四个 major 的产物。

破坏性确认契约三个载体，一条清点口径
ActionMenuItem
danger: true 必须给 confirm 或写明 confirmExempt 理由
BulkActionBarItem
同上。批量条误删的是当前选中的全部，门槛只高不低
Button / ActionButton
variant="destructive" 必须写 confirmExempt；要拦就换 DestructiveButton
ConfirmDestructive
四项契约：verb / target / consequence（必填）/ preconditions
清点
grep -rn confirmExempt portals/ —— 已声明豁免的红色动作，逐条带理由

destructive-strong 不在契约内：它是落锤档——确认对话框里的那个提交按钮。要求落锤自己再确认一次是循环。

前置条件三态DestructivePrecondition

met 是唯一门闩，放不放行由调用方判；unknown 只管把「查不到」和「确认没满足」在视觉上分开（灰问号 vs 红叉）。分开是有意的——「读不到检查单时挡住还是放行」是产品的风险判断，DS 收下就等于把风险偏好焊进来。

文案出口英文托底，应用必须传参

每一处渲染文字都换得掉，含 aria-label 与 sr-only。三档收法：一两条走独立 prop，三条以上走 labels 对象，拼接出来的句子收模板不收词（titleTemplate / selectionTemplate）——语序是语法，不是词汇。默认值一律英文，且它只是托底：英文默认值出现在生产界面上，说明有人忘了传。

04清单之外边界

不会进这份清单的
  • 带业务归属的面板——UserPanel / TenantPanel 一类，归 domain 层
  • 带产品专名的件——没有 console-* / admin-* 前缀
  • 业务状态映射——把「订阅逾期」映射成 warning 是产品的判断
  • 认证策略——step-up / TOTP 由产品接在 onConfirm 返回的 Promise 上
收录门槛

「可被产品侧二次封装」是允许项不是门槛。真正的门槛是产品实据：一个件要进来，得先在多个消费方里被各自重写过。一个件如果只有一个产品用得上，它就还没到进 DS 的时候。

这份清单说的是「有什么」，不是「谁在用」。消费方装了哪版、迁到哪一步，那份数据不在本仓——DS 看不到 portals 的 lockfile，写出来的第一天就是过期的。宁可缺一份文档，也不要一份看起来权威、实际过期的文档。
