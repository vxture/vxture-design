发版说明

升到 design-system 12.8.1 要做什么、不用做什么。从 10.x 上来会跨两次 major（11.0.0、12.0.0），要改的都在表格列对齐这一族——§02 是清单。还停在更早版本的，§03（10.0.0 的间距档）与 §04（9.0.0 的红色按钮）按顺序补。

01现在该装什么2026-09-15 · minor

应用只装伞包。直接装 design-ui 拿不到运行时接线（主题 / 密度 / 字号 provider），且版本约束不再由伞包保证。

包版本这次动了吗
@vxture/design-system13.4.0major 应用侧主依赖，装这个
@vxture/design-ui10.3.0major 删除每页条数的 auto 档（§02）；新增 FieldValue 与三列 FieldGroup（§05m）；InputOTP 新增形态轴（§05n）；ShellHeader 新增 layout / surface（§05p）； 由伞包精确钉版，不要直接装；新增图标 check-circle / workspace（§05k）、caret-line-left / caret-line-right；Pagination 翻页改图标（§05l）
@vxture/design-tokens3.4.0minor 宽松密度重排（§05i）；title / overline 字重 500、新增 code-lg（§05j）
三个包必须一起升。伞包对另两包钉的是精确版本，装 12.8.1 就会带上 ui 9.5.1 与 tokens 3.3.0；不要单独升其中一个。

从 10.x 上来是跨 major 的：伞包 12.2.0 本身相对 12.1.0 是 minor，但 11.0.0 与 12.0.0 各有一条破坏性变更，见 §02。两条都不报错——一条静默改变已有表格的列对齐，一条把一个联合成员的名字挪给了另一个含义。

Pagination 与 useListPagination 的 "auto"（按可视高度自动算每页条数）全面删除（owner 2026-09-25）。写了 "auto" 的地方升级后类型检查报错；没写的地方不报错，但行为会变，见下表第三行。
原写法升级后要做的
pageSize="auto"类型错误改成具体条数，如 pageSize={20}
pageSizeOptions={["auto", …]}类型错误去掉 "auto"；不传则缺省为 10 / 20 / 50 / 100
useListPagination(rows)不报错，每页从「一屏放几行」变成固定 20 条要别的条数就传第二个参数
useListPagination(rows, "auto")类型错误改成具体条数，或不传（缺省 20）
pageSizeAutoLabel类型错误（参数已删除）删掉这个参数

确认迁完：grep -rn '"auto"' --include=*.tsx 里与分页相关的都已清掉，tsc 通过。另外 ListCard 不再输出 data-list-card 属性（它只给 auto 测量当探针用），若门户自己的样式或脚本依赖过它，需要一并处理。

02b必须改的11.0.0 / 12.0.0 两次 major

两条都在 DataTable 的列对齐上，都不报错。一条静默改变已有表格的观感，另一条会让代码编译通过但含义变了——后者更隐蔽。

① 列对齐的默认值随位置了（11.0.0）

DataTableColumn.align 的缺省从一律 left 改为随位置：首列 left、其余 center。

影响面是「所有没显式写 align 的非首列」。它们从左对齐变成居中，没有任何编译期信号——表格照常渲染，只是看起来不一样了。文本列尤其明显：一列居中的中文描述读起来比左对齐费劲得多。

怎么处理：不是全部加回 align:"left"。新缺省对多数表是对的（短枚举、状态、数量居中更整齐），值得逐表看一眼；只有承载长文本的列需要显式写回 left。

② "numeric" 这个名字换了含义（12.0.0 + 12.1.0）

这一条要连着两个版本一起读，单看任何一个都会得出错误结论：

版本align:"numeric" 的含义
11.x金额档（定宽块）
12.0.0不存在 改名为 "money"，写 "numeric" 编译失败
12.1.0+回来了，但换了意思 纯数值档，与 "money" 并列
直接从 11.x 跳到 12.1.0+ 的，编译器帮不了你。12.0.0 那一步会报错（名字没了），所以只要中途在 12.0.0 停一下就一定会被发现；但一步跨到 12.1.0+，"numeric" 又是个合法值了——代码编过，金额列却按纯数值渲染。

怎么找：
grep -rn 'align: *"numeric"' src/
逐个判断它当初想表达的是金额还是数值：是金额就改成 "money"，是纯数值就原样留着。这一步只能人读，没有机械判据——两种意图在旧代码里长得一模一样。

另外 12.0.0 同批定稿了金额档的呈现（定宽块、居中不贴右缘）、操作列回定宽、排序标换成上下一对箭头；这些不需要调用方改动。

03还没迁完 10.0.0 的看这里间距档

--space-none 不再注册进 @theme，凡是写 p-none / gap-none / pt-none 这类的地方，类名从此不产出任何规则。不报错，只是那处内边距静默变回浏览器默认。

none 是 CSS 全局关键字，在不同属性上含义不同：padding 上我们想表达 0，而 max-width: none 是「无上限」、line-height 的 Tailwind 原义是 1。把字面词 none 登记进 spacing 命名空间之后，凡是读 spacing 档的工具类族都会把 X-none 解析成 0——Tailwind 不区分「这个族的 none 是不是 0」。

实测一个门户的编译产物，14 个 *-none 落到这一档，12 个对、2 个错：

.leading-none { line-height: var(--space-none) }   → 0，应为 1
.max-w-none   { max-width: none;
                max-width: var(--space-none) }     → 0，应为 none
max-w-none 尤其隐蔽。Tailwind 先输出自己的 max-width: none，再被本档覆盖——类名照常生成。「这个类有没有产出」这一类检查全是绿的，只有比对取值才看得见。实际后果：三个门户 18 处 DialogTitle 行高归零、标题与描述叠字，以及对话框写 max-w-none 被夹成 34px 宽。
这条修复的回归断言，覆盖面有个限度，说明白。DS 仓里为它写了两条断言，但只有 leading-none 那条能在本仓自己的编译上跑出来；max-w-none 的双声明只在 Next / Turbopack 里复现——同一段 CSS，不同构建器的产出形态不同。

两者是同一个成因（字面词 none 进了 spacing 命名空间），抓住任一即抓住成因，所以没有为此再搭一套 Next 构建。但这不等于两条都被覆盖了，限度写在了 DS 的代码注释里，这里一并告诉你：如果哪天你的门户换了构建器，max-w-none 这一侧没有回归网接着——那时值得手动比对一次编译产物的取值，而不是只看类名有没有产出。
你写的改成为什么
p-none · px-none · pt-none …p-0 · px-0 · pt-0 …Tailwind 内建档，含义完全相同
gap-none · space-x-nonegap-0 · space-x-0同上
inset-x-none · top-none …inset-x-0 · top-0 …同上
leading-none · max-w-none不用改它们本来就该是 Tailwind 原义，现在才终于是
怎么找：
grep -rnE "(p|px|py|pt|pr|pb|pl|m|mx|my|gap|gap-x|gap-y|space-x|space-y|top|right|bottom|left|inset|inset-x|inset-y)-none" src/

不要连 leading-none / max-w-none 一起改——那两个是这次修复的受益方，不是迁移对象。
为什么不补一个 --leading-none 了事。那不是设计令牌，是为了在名字解析上抢赢 spacing 档而造的影子值——一个叫「none」的行高不表达任何设计决策。而且它只管一族：max-w-none 要再造 --container-none，min-w-none、max-h-none 各自还要一个，每个「CSS 里 none ≠ 0」的属性族都得再补一次。根因只有一个：none 不该是间距档的键名。

04还没迁完 9.0.0 的看这里红色按钮

variant="destructive" 的 Button / ActionButton 现在会编译失败，除非写明为什么不设防。这是「红」与「拦」变成同一个决定的最后一块。

此前判别联合只管 ActionMenuItem 与 BulkActionBarItem，够不到裸的红按钮——于是 grep confirmExempt 会把只有裸红按钮的产品报成「干净」。清单不完整就不能当清单用。

要拦换成 DestructiveButton
<DestructiveButton
  confirm={{
    verb: "Revoke",
    target: passkey.name,
    consequence: "…",
    preconditions: [
      { label: "至少还有一把可用的 passkey",
        met: others.length > 0 },
    ],
    onConfirm: () => revoke(passkey.id),
  }}
>
  Revoke
</DestructiveButton>
不拦写明理由，理由可 grep
<Button
  variant="destructive"
  confirmExempt="确认在流程第二步"
>
  …
</Button>

confirmExempt 收字符串而不是布尔，是为了让「本产品有多少个不设防的红色动作」变成一条 grep。它从不进 DOM。

destructive-strong
不要求。它是落锤档——确认对话框里的那个提交按钮。要求落锤自己再确认一次是循环
DestructiveButton 的限制
不开 variant（按定义就是 destructive 入口档），也不开 asChild（它渲染「按钮 + 对话框」两个节点，塞不进 Slot 的单子元素约束）。AlertDialogTrigger asChild 这类场合用 Button + confirmExempt
variant 是运行时值时
遍历全部挡位的画廊选不出分支，需要回收一次类型——预览面的 galleryVariant 是这个写法的样板

05不用改，但行为变了八个 patch

下面八条不需要你动任何代码，但它们改的是「本来就该这样、此前一直不是」的行为。如果你为这些症状做过绕法，绕法现在可以撤了。

版本症状（你可能见过的样子）绕法可以撤吗
6.0.8Progress 的取值从来没传给过读屏器。色条画在 70% 的位置，但 aria-valuenow 一次都没发出去、data-state 永远停在 indeterminate——听到的是「正在忙」，不是「已完成 70%」。同版还修了 max 不为 100 时填充位置与取值对不上注意 如果你用 [data-state="indeterminate"] 选中「有取值的进度条」，那个判据现在失效了——有取值的会是 loading / complete
6.0.7InputOTPSlot 脱离 <InputOTP> 单独渲染时直接抛 TypeError。件里那个 ?. 从来没生效过——上游 context 的默认值是个真值空对象，短路条件永远不成立可以 如果你为此包过 try/catch 或避开了单独渲染
6.0.6FullscreenProvider：从锁滚动的面板切到不锁的面板，退出后整页滚不动。刷新就好，下次照样注意 如果你为此在退出后手动重置过 document.body.style.overflow，现在可以撤——但要确认没有别的地方依赖那次重置
6.0.5Toast 同一毫秒连发两条时，两条可能共用一个 React key，后一条把前一条顶掉。只在手快时偶发可以 如果你为此自己传过 id——不过自己传 id 一直是合法用法，留着也没问题
6.0.4原生全屏退出时控制台一条 TypeError——exitFullscreen() 被调了两次，第二次时文档已不在全屏态可以 如果你 catch 过它
6.0.3EntryCard 只给 onClick 不给 href 时，鼠标点得到、键盘进不去。而且两者都不给时，卡也一直摆着可点的外观可以 如果你手动补过 role / tabIndex
6.0.2MetricListCard 上焦点停在「更多」按 Enter，菜单不开、详情打开了。鼠标那条路一直是对的，所以这个洞只在键盘上存在可以 如果你在行操作上加过 stopPropagation
6.0.1Drawer 的 width="sm" | "md" | "lg" 一直是死的，一律渲染成 w-full max-w-panel-lg。没有任何报错，DOM 上连那条类都不剩注意 如果你用 className 或内联样式盖过宽度，现在挡位真的生效了，两者会打架
6.0.1 那条值得单独看一眼。挡位失效期间，任何需要窄抽屉的地方只能靠外部盖宽度。现在挡位活了——cn 把 --container-* 登记进了宽度组，你外部再传一个宽度类，谁赢取决于书写顺序，而不是你的意图。升级后请检查所有传了 width 又同时盖过宽度的 Drawer。
6.0.2 文档更正
AlertDialog 的 Esc 是关得掉的。头注此前写「Esc 与点遮罩也不关」，错了一半：Esc 触发 onOpenChange，外点不触发。Esc 能关是对的——没有键盘出路的模态是键盘陷阱。「要求表态」靠的是拿掉随手可点的出口（无 X 钮、外点不关），不是堵死所有出口

05b新增：横排标签的表单行12.4.0 · 只增不改

Field 多了一个方向档 orientation="labeled"：标签左、控件右，两者是 CSS 网格的兄弟轨道。轨道宽走新 token --spacing-field-label-{sm,md,lg}（6 / 9 / 12rem），组件上用 labelWidth 选档，默认 md。

它和已有的 horizontal 不是一回事，别混用。

horizontal 是 flex-row，给开关行 / 复选行用——控件很窄，标签不会被挤。把 w-full 的输入框放进去，中文标签会被 flex 收缩到 min-content，一字宽竖排（2026-09-05 三个门户 86 处就是这个病，那次的结论是「对话框字段一律标签在上」）。

labeled 用的是网格轨道：轨道宽由 token 定、不由内容定，所以标签塌不了。这才是「标签与控件同行」能成立的做法。

什么时候用它

对话框铺双栏字段时（DialogForm size="xl" + grid-cols-2）：标签在上会让每个字段占两行，八个字段就是八行；标签在左则是四行，整表可见、不出滚动条。单栏窄浮层仍用默认的 vertical。

为什么轨道宽是固定值而不是 max-content：两栏并排时左右两侧的标签各自宽窄不同，max-content 会让两栏的控件左边缘错开一截。固定轨道让同一个对话框里所有控件对齐一条竖线。

05c行操作菜单：图标对齐与危险分组12.5.0 · 不用改代码，但菜单会变样

ActionMenu 两处改动，都不需要你动调用代码——但已有菜单的呈现会变。两条都是「本来就该这样」。

① 图标列现在对齐了

此前没图标的项不占位，它的标签直接顶到最左，比同一菜单里带图标的项左移一整个图标宽。现在只要菜单里有任何一项带图标，所有项都占一格。

影响面是「同一个菜单里混着写」的那些。平台上 74 个内联菜单里有 11 个是混的，落在使用者眼里是「这一行没对齐」。

整菜单都没图标的不受影响——纯文字菜单不会凭空缩进一格。

② 尾部的危险动作自动与常规动作分开

separatorBefore 的本意一直是「把危险动作与常规动作分开」，但默认不做、要逐项手写。结果是全站 767 个条目里只有 31 处真写了，而含危险项的菜单有 18 个、其中 16 个的危险项已经排在末尾——判据一直在数据里摆着，却要求每个调用方重复声明一遍。

现在本件自己认末尾那一段连续的危险项，在它前面画线。

separatorBefore 成了三态（既有写法全部照旧）：
· 不写 = 自动判断；
· true = 强制画一条，用于常规动作内部的分组（「增删改」与「上移下移」分两组这种，DS 推断不出来，只有调用方知道）；
· false = 压制自动判断。

已经写了 true 的调用方不受影响：显式值优先，与自动判断落在同一处时只画一条，不会变成两条。
两种情况不自动分隔，是有意的：危险项散在中间时不分——那是调用方的排序问题，逐项加线只会把菜单切碎；整菜单都是危险项时也不分——没有「常规段」可分。

05d新增间距档：栏间沟 7xl12.6.0 · 只增不改

间距梯此前到 6xl 为止，默认密度最大 64px。那是「两个相邻元素之间」的量级；多栏表单要的是另一件事——把两栏分开到视线不会串行。

症状很具体：opera 产品详情页两栏字段在 64px 下，第一栏的输入框看起来仍然贴着第二栏的标签，读者分不清哪个标签管哪个框（2026-09-11 owner 实页走查）。

--space-7xl = 紧凑 96px / 默认 128px。跨度比前面几档大是刻意的：它不是这一梯的下一格，是另一个用途的第一格；放在同一族里只因为它仍由密度轴驱动。

用它，不要写 gap-x-[128px]。arbitrary 值绕过密度轴——紧凑模式下它不会跟着收窄，而那正是密度存在的意义。消费方仓的 ds/no-app-tailwind-arbitrary-scale 也会拦。

05e新增：选文件 FileTrigger12.7.0 · 只增不改

<input type="file"> 是浏览器唯一的文件入口，而它的原生外观无法跟随设计系统。于是每个需要上传的页面都会做同一件事：把原生 input 藏起来、用一个自家按钮触发它——也就是每个应用仓里都会出现一个裸的 <input>。

这件的诞生原因就是被守卫拦了一次。ds/no-app-native-primitive 拦下了 opera 里一个上传图标用的原生 file input，而它的提示写着「DS 不足时先补 DS」。守卫是对的：这不是某个应用的特殊需求，是所有上传场景共有的形状。

两处不显眼但要紧的

藏法用 sr-only 不用 display:none：后者在部分浏览器里让表单控件拿不到键盘焦点，"用键盘打开文件选择器"这条路就断了。触发按钮用 <label htmlFor> 关联——那是不靠 JS 就能让别的元素触发 input 的唯一方式。

每次选完清空 value：同一个文件连选两次时 change 不会再触发（值没变），用户看到的是"第二次点了没反应"——而这恰恰发生在"上传失败了再试一次"的时候。

变体刻意不收 destructive 两档。选一个文件永远不是破坏性动作，而那两档在 ButtonProps 的判别联合里要求同时给出确认或豁免理由。从类型上排掉，本件就不可能成为绕开那条契约的入口——ActionButton 当年是靠换 DistributiveOmit 才堵上同一个洞。

05f表格三根固定列统一 64px12.8.0 · 不用改，观感变了

DataTable 的选择列、序号列、操作列此前借的是控件高度族 w-control-3xl，它随密度平移（紧凑 48 / 默认 56 / 宽松 64）。默认密度下实测选择列与序号列是 56px，操作列被按钮撑到 64px——文件头写着三根同宽 64px，只在宽松密度成立。

12.8.0 起三根列改用新档 w-table-col-fixed：固定 64px，不随密度变化（owner 2026-09-15）。列宽是版面结构，与 sidebar / header 同类，不是控件尺寸。
调用方一行不用改，这三根列由 selectedKeys / indexStart / rowActions 给出、宽度由件决定。可见差异：默认密度下选择列、序号列各宽 8px；紧凑密度下三根列各宽 16px。

07报错查到 DS 头上时先做对照组

这一节是 2026-08-26 一次真实误判的产物，写在这里是因为它会再发生。

消费端报来一条 React key 警告，追进 DS 的构建产物，看到 Section 用的是 jsx 而不是 jsxs，结论是「根因在 DS，改一个字符就行」，并登记了技术债等 DS 修。结论是错的，而链条讲得通——这正是它值得记下来的原因。
对照组结果
<Section>{a}{b}{c}</Section> 静态多孩子不报警
中间层拼数组 → 交给 Section报警
中间层拼数组 → 交给裸 <div>（DS 完全不参与）同样报警
中间层改用带 key 的 Fragment → 交给 Section不报警

裸 <div> 报的是同一条，所以跟 DS 无关。第一行同样关键：Section 内部对 children 用 jsx 并不引发警告——静态多孩子在外层 jsxs(Section, …) 那一步就被标记成已校验了。这也是为什么 React 生态里成千上万个包 children 的组件不会集体刷屏。

为什么会查到 DS 头上

React 的警告原文点了两个名字，恰好都不是真凶：

Check the render method of `Section`.
  ← 收下这个数组的件（DS 的）

It was passed a child from AccountDetailPage.
  ← 元素被创建的地方（你的页面）

真正拼出无 key 数组的中间层一个字都没被提到。顺着两个名字走，一个通向 DS，一个通向页面，中间层正好被跳过。

这条警告不该被压掉

它指向的是真会咬人的东西。[a, b].filter(Boolean) 少一个成员时，后面的会落到前面的索引上，React 按索引复用实例——同类型的兄弟之间状态会串：

[改动前]   A:0  B:3   ← 把 B 的计数器点到 3
[A 消失后] B:0        ← B 落到索引 0，捡了 A 那一格

DS 不会用 Children.toArray 之类的手法把它吃掉：那等于把你的真缺陷盖住。DS 保证的是自己不出这个形状——测试基座现在把 key 警告一律判失败，189 条用例零警告。

规矩：怀疑 DS 是根因时，先造一个不含 DS 的对照组。症状在对照组里照样出现，讨论就结束了；照样不出现，才轮到看 DS 的实现。这比读三层调用链快，也比读构建产物可靠——产物里的 jsx / jsxs 是编译器按调用点决定的，不是作者的选择。
